## 1. 目标与技术前提

### 1.1 推理端要交付的能力

| # | 能力 | 对外表现 |
|---|---|---|
| 1 | 人员检测与跟踪 | `VIS_TARGET`(含稳定 track_id、bearing、粗距离) |
| 2 | 障碍物检测 | `VIS_OBSTACLE` |
| 3 | 人脸识别 | `VIS_FACE`(known / unknown + face_id) |
| 4 | 手势识别 | `VIS_GESTURE`(9 种手势,已去抖) |
| 5 | 声源方向 | `AUDIO_BEAM`(可后置) |
| 6 | 表情显示与触摸 | 接收 `DISP_EXPR`、上报 `TOUCH_EVENT` |
| 7 | 视频上行 | `VIDEO_CHUNK` → C5 |
| 8 | 能力位上报 | `VIS_MODE_STATE`(安全相关,见 §5.2) |

**不属于本方案**:C5 的云端逻辑、STM32 的运动控制、机械与电源。

### 1.2 必须先确认的版本前提(不确认就别开工)

| 项 | 要确认什么 | 为什么 |
|---|---|---|
| ESP-IDF 版本 | 同时支持 P4 与 C5 的版本线;P4 的 MIPI-CSI/DSI 驱动是否已合入 | 决定摄像头与屏能不能用 |
| AI 框架 | P4 上官方推荐的推理框架与其版本 | 决定模型格式与转换工具 |
| 模型库 | 该版本可用的检测 / 人脸 / 关键点模型清单 | 决定四任务能否落地 |
| 摄像头模组 | P4 兼容型号、接口与供电要求 | 决定采集分辨率与帧率上限 |
| 屏与触摸 | 480×480 incell 的 DSI 时序、触摸控制器型号与 I2C 地址 | 决定显示驱动工作量 |
| PSRAM 容量 | 所用模组的实际 PSRAM 大小 | 直接决定 §2.4 的内存预算是否成立 |

> 这几项在文档 02 §8 与文档 06 §2 里已是"打样前阻塞项"。**本方案的所有具体数值都建立在这些前提之上**,前提变了要回来重算。

### 1.3 与已定架构的接口约定(谁产生什么)

| 数据 | 产生方 | 消费方 | 频率 |
|---|---|---|---|
| 原始帧 | P4 摄像头 | P4 推理 / 编码 | 15-30fps |
| 检测 / 跟踪结果(结构体) | P4 | P4 policy | 每帧 |
| 运动意图(速度 / 姿态) | P4 policy | STM32(gait) | 10-20Hz |
| 能力位 | P4 | STM32(限速决策) | 状态变化时 + 1Hz 心跳 |
| 表情指令 | STM32 或 policy | P4 显示 | 事件驱动 |
| 触摸事件 | P4 显示子系统 | STM32 | 事件驱动 |

**关键约定**:P4 只产出"语义",绝不产出关节角;STM32 只消费语义词,不关心模型细节。

## 2. 系统分解:数据流、线程与预算

### 2.1 七段数据流

```
① 采集        摄像头 → 帧缓冲(PSRAM,驱动侧环形)
② 前处理      letterbox / 裁剪 / 缩放 / 色彩 / 归一化 → 模型输入张量
③ 推理        模型前向 → 原始输出张量
④ 后处理      decode + NMS → 检测框列表
⑤ 跟踪        IoU 匹配 + ID 管理 → 稳定轨迹
⑥ 策略        模式 FSM + 能力位 + 意图生成
⑦ 输出        协议上报 / 显示叠加 / 视频编码
```

每一段都要回答三个问题:**缓冲从哪来、能不能零拷贝、跑在哪条任务上**。

| 段 | 缓冲来源 | 零拷贝机会 | 任务与核 |
|---|---|---|---|
| ① 采集 | 驱动侧环形,建议 3 缓冲 | 驱动直接写 PSRAM,CPU 不参与 | cam_task 核 1(阻塞等帧) |
| ② 前处理 | 一块张量缓冲(约 300KB) | 若 ISP / 2D 硬件能做缩放与色彩,整段移到硬件 | 并入 infer_task |
| ③ 推理 | 张量缓冲 + 输出缓冲 | 框架支持外部内存输入时省一次拷贝 | infer_task 核 1 |
| ④ 后处理 | 栈上小数组(≤16 框) | 数据很小,不必强求 | 并入 infer_task |
| ⑤ 跟踪 | 静态轨迹数组 | 无 | infer_task(与④同线程) |
| ⑥ 策略 | 静态状态机 | 无 | policy_task 核 0(20Hz 足够) |
| ⑦ 输出 | 编码器 / 显示各自缓冲 | 显示用叠加而非重绘 | link / disp / stream 任务,核 0 |

**为什么⑤放在推理线程**:跟踪数据量极小(几 KB),单独线程的同步开销大于收益,且与推理结果强时序相关。

**为什么⑥抽出来**:策略要做时间窗判断(手势去抖、目标丢失计时、模式切换),这些逻辑与帧率无关,放 20Hz 的独立任务更稳定,也避免把 policy 的抖动带进推理周期。

### 2.2 线程与核分配(基线)

P4 是双核,**图像通路独占一核,系统与外设放另一核**。

| 任务 | 核 | 优先级 | 触发 | 说明 |
|---|---|---|---|---|
| cam_task | 1 | 高 | 阻塞等帧(超时 100ms) | 只做取帧与入队 |
| infer_task | 1 | 高 | 队列驱动 | 前处理 + 推理 + 后处理 + 跟踪 |
| policy_task | 0 | 中 | 50ms(20Hz) | 模式 FSM、能力位、意图 |
| link_task | 0 | 中高 | 事件 | 与 STM32 和 C5 的协议收发 |
| disp_task | 0 | 低 | 事件 + 33ms | 表情与叠加(可降到 20fps) |
| audio_task | 0 | 中 | 阻塞等 I2S DMA | 采集与声源方向 |
| stream_task | 0 | 低 | 队列驱动 | 编码与分片上行 |
| monitor_task | 0 | 最低 | 1s | 统计与日志 |

**三条硬规则**

1. **推理与采集不得与显示、音频同核**——显示刷新是周期性的带宽与 CPU 消耗者,混在一核会造成规律性卡顿
2. **link_task 优先级要高于显示与推流**——它是安全相关通道(能力位与急停)
3. **任何任务都不得在运行时做大块内存分配**——全部缓冲在开机时一次性分配

### 2.3 队列深度与丢帧策略

| 队列 | 深度 | 满时策略 | 理由 |
|---|---|---|---|
| 采集 → 推理 | 1 | **丢最旧,保最新** | 实时性优先;处理旧帧等于直接增加延迟 |
| 推理 → 策略 | 4 | 丢最旧 | 策略只需最新状态 |
| 策略 → 链路 | 8 | 安全类不丢,遥测类丢最旧 | 能力位与急停绝不能丢 |
| 编码 → 上行 | 2 | 丢最旧 | 视频宁掉帧也不要堆积 |

**必须统计并暴露的计数**:采集帧数、推理帧数、各级丢弃数、推理耗时(均值 / p95 / 最大)、切换次数与耗时。没有这些数字就无法定位瓶颈,它们同时是文档 06 中 EC-01/EC-07 的验收依据。

### 2.4 缓冲与内存预算(估算,需按实际模组核对)

| 项目 | 计算 | 占用 |
|---|---|---|
| 采集帧缓冲(720p YUV422 × 3) | 1280×720×2B×3 | **5.5 MB** |
| 模型输入张量(320×320 RGB888) | 320×320×3 | 0.31 MB |
| 常驻模型权重(3 个槽位) | 每槽位按 1-3MB 估 | **3-9 MB** |
| 显示双缓冲(480×480 RGB565 × 2) | 480×480×2×2 | 0.92 MB |
| 显示图层缓存 | 复用 + 1 层 | 0.46 MB |
| 视频编码缓冲 | 码流环形 | 1-2 MB |
| **合计(PSRAM)** | | **约 11-19 MB** |

**结论**:若模组只有 16MB PSRAM,上表已接近上限。三条必须遵守的约束:

1. **模型槽位最多 3 个**,优先把"人 + 障碍"合并成一个多类模型(直接省一个槽位)
2. **不要盲目上 1080p 采集**:1080p YUV422 单帧 2.76MB,三缓冲就是 8.3MB
3. **内部 SRAM 只放栈、队列、小结构体**,任何帧级缓冲都不许放进去

### 2.5 带宽预算(真正的隐形瓶颈)

| 通道 | 计算 | 估算带宽 |
|---|---|---|
| 采集写入 | 1.84MB × 30fps | 55 MB/s |
| 推理读取(帧 + 张量) | 约 2MB × 15fps | 30 MB/s |
| 显示刷新 | 0.46MB × 60fps | 28 MB/s |
| 视频编码读取 | 1.84MB × 30fps | 55 MB/s |
| **合计** | | **约 170 MB/s** |

PSRAM 的可用带宽有限,**同时开满采集、显示、编码与推理,很可能把所有环节一起拖慢**。三条设计约束:

1. **显示不要 60fps 全屏重绘**:表情变化不快,按变化刷新或 20fps 即可;能局部叠加就不重绘整帧
2. **不需要视频时关掉编码**:`VIDEO_CTRL` 就是干这个的
3. **采集帧率按需降级**:静止交互态可降到 10-15fps

> 这张表是**估算**,必须以 EC-01/EC-07 的实测数据替换。若实测发现带宽是瓶颈,优先砍显示与编码,**不要砍推理分辨率**——那会直接影响安全功能。

## 3. 模型方案

### 3.1 四个任务的模型候选与选型方法

以下候选全部标**待验证**——在你给出具体的 ESP-IDF / AI 框架版本之前,无法确认哪个模型在 P4 上真实可用。**选型方法比候选名单更重要。**

| 任务 | 候选路线 | 输入尺寸(建议) | 选型方法 |
|---|---|---|---|
| 人员 + 障碍检测 | **一个多类检测模型**(首选),或两个单类模型 | 320×320 或 416×416,int8 | 先确认框架自带哪些检测模型与权重;对比"多类"与"两个单类"的帧率差 |
| 人脸识别 | 人脸检测(小输入)+ 特征提取小网络 | 检测 160-240,特征 112×112 | 优先用框架自带的人脸检测与识别示例,不要自己训练检测器 |
| 手势识别 | 手部检测 / 关键点 + 时序分类,**或**端到端时序模型 | 关键点方案 224×224 | 先做关键点方案:更可控、可调试、可分阶段验证 |
| 障碍物(补充) | 检测"障碍物类"+ 可通行区域;或加 ToF 兜底 | 同检测模型 | 见 §4.7 |

**选型的三个硬约束**

1. **优先复用框架自带模型**——自己训练检测器在嵌入式上是很长的路,先用官方权重跑通闭环
2. **必须量化到 int8**——否则帧率通常不够;量化后必须做精度对齐测试
3. **多类优先于多个单类**——省一次完整推理,且从结构上消除"跑人检测时没跑避障"的缺口

### 3.2 分阶段切换:槽位与能力位

| 槽位 | 内容 | 常驻? | 能力位 |
|---|---|---|---|
| slot0 | 多类检测(人 + 障碍) | **是(安全相关)** | PERSON + OBSTACLE |
| slot1 | 人脸检测 + 特征提取 | 建议常驻 | FACE |
| slot2 | 手势(手部 + 关键点 + 时序) | 可常驻,也可按需 | GESTURE |

| 模式 | 用哪个槽位 | 目标帧率 | 能力位 | 安全含义 |
|---|---|---|---|---|
| IDLE | slot1(低频) | 1-5fps | FACE | 静止,无碰撞风险 |
| ACTIVE | slot0 + slot1 | 10fps | PERSON+OBSTACLE+FACE | 准备交互 |
| **FOLLOW** | slot0 | ≥15fps | **PERSON+OBSTACLE** | 移动中,避障必须开 |
| PATROL | slot0 | ≥15fps | OBSTACLE(可加 PERSON 低频) | 移动中,同上 |
| INTERACT | slot2 + slot1 | 10fps | GESTURE+FACE | **必须静止才允许** |

### 3.3 切换实现要点(三个容易踩的坑)

**坑 1:切换不只是换模型指针,前处理参数也必须一起换。**

不同模型的输入尺寸、是否 letterbox、归一化方式、色彩顺序可能都不同。所以"槽位"应是一个结构体,包含权重指针 + 前处理参数 + 后处理类型 + 输出解析方式,而不是只存一个模型句柄。

**坑 2:切换期间的能力位要保守。**

切换没完成前新能力还没生效。`VIS_MODE_STATE` 在切换期间应上报**取交集**(旧能力 ∩ 新能力),而不是直接报新能力,否则 STM32 会提前放开速度。

**坑 3:跟踪器不要无脑重置。**

切到人脸或手势时,人员轨迹应尽力保留(切回来时不用重新锁定)。建议只重置"新槽位不支持的类别"的轨迹。

### 3.4 量化与转换流程(每步都要留证据)

| 步骤 | 输入 | 成功判据 | 失败怎么办 |
|---|---|---|---|
| 1. 模型信息核对 | 原始模型文件 | 得到输入输出形状、算子清单、参数量 | 保存完整报告 |
| 2. 转换 | 框架要求的中介格式 | 转换器返回 0,无未支持算子 | **保存工具版本、完整命令、报错节点原文**(负面结论也要留证据) |
| 3. 量化 | 校准数据集(200-500 张真实场景图) | 量化后精度下降在阈值内 | 换逐层 / 混合量化,或调整校准集 |
| 4. 板上精度对齐 | 同一批测试图 | 板端输出与 PC 端差异在阈值内 | 定位是前处理差异还是量化误差 |
| 5. 板上性能 | 板 + 摄像头 | 帧率与延迟写入实验卡 | 降分辨率或换模型,不要先下"不可行"结论 |

**校准集必须来自真实场景**(你的房间、你的光照、机器人的实际视角)。用公开数据集的图会让量化精度虚高。

## 4. 关键算法与参数

### 4.1 前处理(最容易出错的一段)

```
输入:采集帧(1280x720)
步骤:等比缩放 → 补边(letterbox) → 色彩转换 → 归一化 / 量化 → 写入张量
必存:scale_x, scale_y, pad_x, pad_y
```

**必须保存缩放与补边参数**,后处理要把框坐标映射回原图。这是检测类项目最高频的 bug:**框整体偏移或整体缩小**,几乎都出在这里。

| 注意点 | 说明 |
|---|---|
| 等比缩放 | 不要直接拉伸,否则目标在不同宽高比下形状变化,精度下降 |
| 补边颜色 | 用中性灰(如 114),与训练时保持一致 |
| 归一化 | 严格按训练时的 mean/std 或量化参数;int8 模型通常直接输入 uint8 减零点 |
| 硬件加速 | 若框架 / ISP 支持硬件 resize 与色彩转换,优先用,省 CPU 也省带宽 |

### 4.2 后处理

| 参数 | 建议初值 | 说明 |
|---|---|---|
| 置信度阈值 | 0.35-0.5 | 人检测可低些(误检靠跟踪过滤),手势要高 |
| NMS IoU 阈值 | 0.45-0.5 | 过小会把相邻的人合并 |
| 最大输出框数 | 16 | 与协议 / 缓冲上限一致 |

**建议**:后处理输出统一为 `{cls, conf, x, y, w, h}` 的定长数组(不超过 16 个),让跟踪与策略完全不用关心模型细节。

### 4.3 跟踪(让画面"稳"下来的关键)

最简可行方案,不要一上来就上复杂跟踪器:

| 环节 | 做法 |
|---|---|
| 匹配 | 同类别内按 IoU 贪心匹配(阈值 0.3);或加一阶速度预测后再匹配 |
| 新建 | 未匹配的检测新建轨迹,需连续 2 帧确认(min_hits=2) |
| 维持 | 未匹配的轨迹保留最多 15 帧(30fps 下约 0.5s),期间计为暂失 |
| 删除 | 暂失超过上限则删除,并发 `VIS_TARGET_LOST` |
| ID | 单调递增;回绕时跳过 0(0 保留为"无") |

**为什么 min_hits=2**:单帧误检会瞬间产生一堆假 ID,策略层会跟着抖。两帧确认能滤掉大部分。

### 4.4 bearing 与距离估计(跟随控制的实际输入)

| 量 | 算法 | 精度 |
|---|---|---|
| bearing(水平角) | `atan2(x_center - cx, fx)`,cx / fx 由标定得到 | 可达 ±0.5°(标定准确时) |
| 距离(粗估) | 针孔模型:以人体高度为已知尺寸,`distance ≈ fy × H_real / bbox_h` | 误差 20-40%(受姿态与遮挡影响) |

**两条必须写进设计的结论**

1. **跟随控制主要用 bearing,距离只做"太近 / 太远"的分档判断**。用粗估距离做 PID 会被噪声带偏。
2. **摄像头标定必须做一次**:至少标出 `fx, fy, cx, cy`;要做精确一点再加畸变参数。棋盘格一次标定即可,结果存 Flash。

### 4.5 手势识别的时序去抖(必须做)

单帧手势极易误触发,所以要三道闸:

```
闸 1:置信度阈值(高,如 0.6)
闸 2:时间窗投票(最近 8 帧中至少 5 帧一致)
闸 3:冷却时间(同一手势发出后 1s 内不重复发)
```

另外两个实用约束:

- **只在静止的 INTERACT 模式启用手势**——移动中手势既不可靠也不安全
- **手势 ID 语义已在协议里定义**(文档 03),不要自己另起编号

### 4.6 人脸:注册与匹配阈值

| 环节 | 做法 |
|---|---|
| 检测 | 用框架自带人脸检测,输出框 + 关键点 |
| 对齐 | 用双眼关键点做仿射对齐后再提特征(对识别率影响很大) |
| 特征 | 小网络输出定长向量(如 128 / 256 维) |
| 注册 | 每人存 3-5 张不同角度 / 光照的特征 |
| 匹配 | 余弦相似度,阈值先取 0.5-0.6,**必须在真实场景下调** |
| 存储 | 特征存 NVS 或文件系统;注意隐私边界(文档 04 §5.2) |

**不要用识别结果做安全决策**(例如"是主人所以可以靠近"),它只用于交互体验。

### 4.7 障碍物检测的现实约束

**这一项要明确提醒**:单目视觉做"可通行性判断"比做"人检测"难得多,而它现在是安全相关的。

| 路线 | 优点 | 风险 |
|---|---|---|
| 检测"障碍物类" | 与现有检测管线复用,实现简单 | 只能识别训练过的类别;地面坑洞、细腿、玻璃完全看不到 |
| 可通行区域分割 | 泛化更好 | 模型更大、帧率更低 |
| **加一颗 ToF / 超声兜底** | 对近距离空地与坑洞有直接测量 | 增加硬件成本(约 20-60 元) |

**建议**:先做检测类路线跑通闭环,但**保留一条"是否需要加 ToF 兜底"的决策项**,并在 EC-07 中专门测"未训练过的障碍物"的漏检率。对一台会走路的机器人,纯视觉避障的安全性不足以让人放心。

## 5. 与 STM32 的接口落地

### 5.1 只用品已定义的消息(不要自创)

| 方向 | 消息 | 用途 |
|---|---|---|
| P4 → STM32 | `VIS_TARGET` / `VIS_TARGET_LOST` | 跟踪结果 |
| P4 → STM32 | `VIS_OBSTACLE` | 障碍列表 |
| P4 → STM32 | `VIS_FACE` / `VIS_GESTURE` | 人脸与手势 |
| P4 → STM32 | `VIS_MODE_STATE` | **能力位(安全相关)** |
| STM32 → P4 | `CMD_VIS_MODE` | 请求模式与最低能力要求 |
| STM32 → P4 | `VIS_TRACK_CMD` | 指定跟随目标或关闭跟随 |
| P4 → STM32 | `AUDIO_BEAM` / `TOUCH_EVENT` | 声源方向、触摸 |
| C5 → P4 | `VIDEO_CTRL` | 开关视频上行 |
| P4 → C5 | `VIDEO_CHUNK` + `VIS_FRAME_META` | 视频分片上行 |

字段定义见文档 03 与 `robot_link.h`。**实现时直接 include 那个头文件,不要手抄结构体。**

### 5.2 能力位规则(P4 侧要实现的部分)

| 规则 | P4 的行为 |
|---|---|
| 上报实际状态,不上报意图 | `caps` 必须是"当前真正在跑的模型能力" |
| 切换中取交集 | 切换未完成时上报 旧能力 ∩ 新能力 |
| 状态变化立即上报 | 切换完成、模型加载失败、能力退化都要立刻发 |
| 心跳保活 | 至少 1Hz 上报一次;超时会被 STM32 按能力位 0 处理 |
| 拒绝违规请求 | 收到要求关闭避障但机器人非静止时,返回错误码而不是照做 |

> 最后一条很重要:P4 侧也要有这道自检,形成"双侧约束"。单侧约束一旦有 bug 就没有兜底。

### 5.3 心跳与健康

| 项 | 建议 |
|---|---|
| 心跳内容 | 当前模式、能力位、推理耗时、丢弃计数、温度(可读时) |
| 频率 | 1Hz(与 STM32 的 200ms 失联阈值相比足够宽松) |
| 告警 | 连续推理超时、槽位加载失败、内存不足,都要上报一次并在日志留证据 |

## 6. 分阶段实施计划

每一步按"输入 → 产出 → 验收 → 失败怎么办"执行;**不达标不要往下走**。工作量为**估算**,单位人日。

| # | 阶段 | 产出 | 验收判据 | 失败怎么办 | 估算 |
|---|---|---|---|---|---|
| 0 | 环境与前提确认 | SDK / 框架 / 模型清单 / 硬件清单 | 能列出可用检测模型与摄像头驱动状态 | 版本不支持就换版本线,不要硬改 | 2-4 |
| 1 | 摄像头采集闭环 | 稳定取帧并打印帧率 / 分辨率 | 连续 10min 不掉帧、无错误 | 查 CSI / DSI 引脚与时序,核对供电 | 3-5 |
| 2 | 单模型推理闭环 | 跑通框架自带检测模型并输出框 | 板上输出合理检测结果 | 保存转换与运行 log,逐个解决 | 5-8 |
| 3 | 前处理与坐标映射 | 框位置与画面一致(屏上叠加验证) | 目视框贴合目标,无明显偏移 | 检查 letterbox 参数与反映射公式 | 2-3 |
| 4 | 后处理 + 跟踪 | 稳定 track_id,短暂遮挡后能接上 | 连续 100 帧 ID 不跳变 | 调 IoU 阈值与 min_hits | 3-5 |
| 5 | 槽位与切换 | 多模型常驻 + 指针切换 + 能力位上报 | 切换 ≤200ms,切换中能力位保守 | 见 §3.3 三个坑 | 4-6 |
| 6 | 链路联调 | 与 STM32 互发 `VIS_TARGET` / `VIS_MODE_STATE` | 用 PC 参考工具交叉验证,零 CRC 错误 | 核对字节序与结构体打包 | 3-5 |
| 7 | 人脸 | 检测 + 对齐 + 特征 + 注册 / 匹配 | 5 人各 5 张,室内识别率可接受 | 先解决对齐,再调阈值 | 5-10 |
| 8 | 手势 | 手部 → 关键点 → 时序 → 去抖 | 9 种手势各测 30 次,误触发率可接受 | 先只做 3-4 种常用手势 | 10-20 |
| 9 | 障碍物 | 障碍检测 + 能力位接入 | 见 EC-07 判据 | 考虑加 ToF 兜底 | 5-15 |
| 10 | 显示与触摸 | 表情动画 + 触摸事件 + 瞳孔跟随 | 触摸到上报 <50ms,表情流畅 | 降低刷新率或简化图层 | 5-8 |
| 11 | 音频与声源 | 4 麦采集 + 声源方向 | 声源方向误差在可接受范围 | 先用最简单的 DOA 算法跑通 | 8-15 |
| 12 | 视频上行 | 编码 + 分片 + 流速控制 | 720p 可连续上行且不阻塞推理 | 降码率或降分辨率 | 5-8 |
| 13 | 性能优化 | 达到 EC-01 / EC-07 的帧率与延迟目标 | 实测达标并记录 | 按实测瓶颈逐项优化 | 5-10 |
| | **合计** | | | | **约 65-115 人日** |

**最小可用闭环**:第 0-6 步(约 20-35 人日)做完,就有了"看得见人、跟得上、与 STM32 说得上话"的可用系统。**建议先交付这个闭环,再补人脸 / 手势 / 音频。**

## 7. 测试与调试方法

### 7.1 台架测试(强烈建议)

推理端 90% 的工作可以在**不装机器人**的情况下完成:P4 开发板 + 摄像头 + 屏 + USB 线即可。台架阶段就要把下面这些测完,否则装到机器人上后问题会混在一起。

| 测试 | 方法 | 判据 |
|---|---|---|
| 帧率 | 连续跑 30min,统计平均 / 最低帧率 | 无规律性跌帧 |
| 推理耗时 | 每帧打时间戳,统计 p95 与最大值 | 最大值不比均值差太多(否则有调度问题) |
| 丢帧 | 统计各级丢弃计数 | 稳态下接近 0 |
| 内存 | 跑 2h 观察剩余内存曲线 | 不持续下降(无泄漏) |
| 坐标映射 | 屏上叠加框 | 目视贴合 |
| 跟踪 ID | 目标走 S 形、被遮挡 1s | ID 不跳变 |
| 切换 | 反复切模式 100 次 | 无失败、无内存增长 |
| 长稳 | 连续跑 8h | 无重启、无错误累积 |

### 7.2 必须建立可重复的评估集

**这一项经常被跳过,但它决定你能不能客观判断"改好了还是改坏了"。**

| 数据集 | 内容 | 用途 |
|---|---|---|
| 检测集 | 200-500 张真实场景图(你的房间、不同光照、含人与障碍) | 精度评估、量化对齐 |
| 视频集 | 5-10 段各 30s(跟人走动、有人遮挡、有手势) | 跟踪与帧率评估 |
| 手势集 | 9 种手势 × 多人 × 各角度 | 手势验收 |
| 人脸集 | 5-10 人,各 5 张(不同光照 / 角度) | 识别率与阈值标定 |

每次改模型或改参数,都用同一套数据跑一遍并记录指标。**没有这套数据,你只能靠"感觉好像好一点"来判断,这在工程上等于没测。**

### 7.3 插桩(从第一天就做)

| 项 | 建议 |
|---|---|
| 时间戳 | 每帧记录采集、前处理完成、推理完成、后处理完成时刻(微秒) |
| 帧号 | 全链路统一 frame_id,便于把日志与画面数据对上 |
| 计数器 | 见 §2.3 |
| 可回放 | 支持"用录制帧喂管线"的模式,不依赖摄像头也能复现问题 |
| 协议交叉验证 | 用 `tools/robot_link_ref.py` 解码实机报文,确认字段与字节序 |

> 最后一条项目里已具备条件:参考实现与头文件的布局断言都验证通过,可以直接当"协议裁判"。

### 7.4 出问题时按这个顺序查

```
1. 数据对不对?     -> 把帧 dump 出来看(或屏上显示)
2. 前处理对不对?   -> 把送进模型的张量 dump 成图,应该看得出目标
3. 模型输出对不对? -> 把原始输出张量 dump,手工解码一两个框
4. 坐标映射对不对? -> 屏上叠加,目视
5. 跟踪对不对?     -> 打日志看匹配关系
6. 协议对不对?     -> 用参考工具解码
7. 性能问题?       -> 看分段耗时,定位是哪一段慢
```

**绝大多数"模型不准"的问题,最后都出在第 2 步。**

## 8. 不要做什么(反模式清单)

按危害排序:

| # | 反模式 | 后果 |
|---|---|---|
| 1 | 在移动状态下关闭避障能力位 | 安全事故;必须由 STM32 强制限速兜底 |
| 2 | 运行时从 Flash 加载 / 卸载模型 | 100-500ms 卡顿,正走着突然"瞎"一下 |
| 3 | 每帧 memcpy 整帧 | 带宽被吃光,所有环节一起变慢 |
| 4 | letterbox 参数只算不存 | 框位置整体偏移,且很难发现 |
| 5 | 用模型替代小腿位置传感器 | 见文档 08:原理上不可辨识,做了也白做 |
| 6 | 采集与显示同核 | 规律性卡顿,帧率上不去还找不到原因 |
| 7 | 用粗估距离做跟随 PID | 距离噪声 20-40%,控制会抖 |
| 8 | 没有评估集就调参 | 无法判断改动有没有变好 |
| 9 | 单帧手势直接触发 | 误报率高,交互体验差 |
| 10 | 把安全保护建立在模型输出上 | 模型失效时保护同时失效;安全必须靠阈值与硬件 |

## 9. 风险与待确认事项

### 9.1 本方案引入的新风险

| # | 风险 | 证据等级 | 缓解 |
|---|---|---|---|
| N1 | PSRAM 带宽不足以同时支撑采集 + 推理 + 显示 + 编码 | 估算 | 按需降级显示 / 编码帧率;实测后再定采集分辨率 |
| N2 | 框架自带模型与本项目任务不匹配(尤其障碍与手势) | 数据不足 | 先跑通官方模型,再评估自训练的必要性与成本 |
| N3 | 手势识别开发量被低估 | 工程推论 | 先只做 3-4 种手势,验收后再扩展 |
| N4 | 纯视觉避障漏检未训练类别的障碍 | 工程推论 | 保留 ToF 兜底决策项 |
| N5 | 切换时前处理参数未同步,导致精度骤降 | 工程推论 | 槽位结构体必须含前处理参数,切换后做一次自检 |

| 2 | P4 模组的 PSRAM 容量 | 决定槽位数量与采集分辨率 |
| 3 | 摄像头模组型号与最高帧率 | 决定采集上限 |
| 4 | 是否接受"先做最小闭环,人脸 / 手势 / 音频后置" | 决定实施顺序与工期 |
| 5 | 是否愿意为避障增加一颗 ToF 兜底 | 决定安全等级与成本 |
