## 1. 总体原则

三个节点各自独立开发、独立烧录、独立版本,只通过 robot_link 协议耦合。

| 原则 | 具体要求 |
|---|---|
| 分层单向依赖 | 应用 → 服务 → 协议 → 驱动抽象 → 厂商适配 → BSP,禁止反向依赖 |
| 核心可 PC 测试 | 协议编解码、逆运动学、步态相位、限幅逻辑不得包含 HAL/IDF 头文件 |
| 静态分配 | 除 ESP32 侧必要的 RTOS 对象外不使用 malloc;缓冲全部静态或调用方提供 |
| 显式状态 | 用状态枚举而非散落的布尔标志 |
| 资源有界 | 每个缓冲、队列、重试次数都有编译期常量上限 |
| 可观测 | 每个模块有计数与状态可读出,禁止黑盒 |

## 3. STM32F407 固件架构

### 3.1 模块划分与对象

| 模块 | 对象/类型 | 职责 | 拥有什么 |
|---|---|---|---|
| BSP | 板级初始化 | 时钟、引脚、电源时序、NVIC | 初始化顺序与硬件资源 |
| IMU 驱动抽象 | imu_t | 读原始数据、自检、配置量程 | 1 个 SPI 句柄、1 个 DMA 缓冲 |
| IMU 适配 | icm42688 适配 | 具体寄存器操作 | 器件实例 |
| 姿态解算 | attitude_t | 互补滤波 / Mahony,输出 roll/pitch/yaw | 内部状态 |
| 关节抽象 | joint_t | 统一的"设定角度 / 读回角度"接口,屏蔽两类舵机差异 | 关节映射表 |
| PWM 舵机驱动 | pwm_servo_t | 角度转脉宽(小腿 6 个 MG996R),含死区量化与限幅 | 校准表、6 路影子寄存器 |
| 总线舵机驱动 | bus_servo_t | 三条半双工总线的异步收发、位置/负载/温度解析 | 每总线环形缓冲、节点表、超时计数 |
| 逆运动学 | ik_t | 足端坐标转 3 关节角 | 机械常数(编译期) |
| 步态引擎 | gait_t | 速度与姿态意图转 6 足轨迹转关节角 | 步态相位、支撑足掩码 |
| 意图信箱 | motion_intent_t | 单写单读,最新意图加版本号 | 1 个结构体加版本计数器 |
| 安全仲裁 | safety_t | 优先级判定、急停、失联、限幅 | 状态机、错误标志 |
| 链路 | rl_link_t 两实例 | 协议收发 | 环形缓冲(静态) |
| 电源管理 | power_t | 采样、电量、低电阈值 | 滑窗缓冲 |
| 监督 | supervisor_t | 健康计数、看门狗、任务存活 | 计数器 |

### 3.2 意图信箱:链路与控制的解耦点

```c
typedef struct {
    uint32_t version;          /* 每次写入递增,读者据此判断是否有新意图 */
    int16_t  vx_mm_s;
    int16_t  vy_mm_s;
    int16_t  wz_mrad_s;
    uint16_t duration_ms;
    uint8_t  gait;
    uint8_t  flags;
    uint32_t last_update_ms;   /* 用于超时判定 */
} motion_intent_t;
```

规则:

- 只有 comm_task 写,gait_task 只读
- 写入采用"版本号加结构体"两段写,读者比对版本号判断一致性(单核下加临界区即可)
- gait_task 每周期读一次,`now - last_update_ms > duration_ms` 时按 flags 处理(减速停止或保持)
- 意图过期不报错,只自然降级,避免链路抖动导致状态机乱跳

### 3.3 任务与调度

| 任务 | 优先级 | 周期 | 关键实现细节 |
|---|---|---|---|
| gait_task | 4(高) | 4ms | 用 vTaskDelayUntil 保证周期稳定;不做 IO;PWM 走影子寄存器一次更新 |
| imu_task | 4(高) | 1ms | 阻塞在 DRDY 二值信号量;SPI 用 DMA;解算只用 FPU 单精度 |
| comm_task | 3 | 事件 | 阻塞在 UART 空闲信号量加消息队列;解析后只写信箱,不直接驱动运动 |
| bus_task | 3 | 事件 + 5ms 轮询 | 三条总线舵机的异步收发;超时标记失效但不阻塞;更新"最后已知位置"表 |
| power_task | 2 | 10ms | ADC 用 DMA 循环加半满中断 |
| supervisor_task | 1(低) | 100ms | 检查各任务计数是否推进,再决定喂看门狗 |

**总线任务的硬性规则(违反会直接破坏实时性)**

| 规则 | 原因 |
|---|---|
| 总线收发**绝不**在 gait_task 里做 | 一次总线超时可达数毫秒,会破坏 250Hz 周期 |
| gait_task 只读"最后已知位置"表 | 该数据可能滞后 5-20ms,对位置反馈足够,对电流保护不够 |
| 每条总线独立超时与重试 | 一个舵机不响应不能拖垮整条总线循环 |
| 发送命令与读取反馈分离 | 命令以固定 50Hz 下发;反馈按总线轮询,不要求同频 |
| 单条总线连续失败 N 次 → 标记该总线失效 | 触发姿态降级(见文档 01 §7.2 失联矩阵) |

看门狗策略:独立看门狗由 supervisor 喂;若 gait_task 或 imu_task 的计数停止推进,则**停止喂狗**,让系统复位并回到安全姿态。不要把喂狗放在最高优先级任务里,否则该任务自身挂死时看门狗失效。

### 3.4 逆运动学与浮点

F407 有单精度 FPU(已确认),IK 用 float 即可,不需要定点化。但注意:

- 编译必须开 `-mfpu=fpv4-sp-d16 -mfloat-abi=hard`,否则 FPU 形同虚设
- 避免 double:Cortex-M4F 无双精度硬件,double 运算会走软件库,性能骤降
- sinf / cosf / atan2f / sqrtf 单精度库函数一次约 20-100 周期;18 关节 250Hz 的预算约 250k 周期/s,占 168MHz 不足 0.2%(估算)

### 3.5 参数与校准数据存储

| 数据 | 位置 | 说明 |
|---|---|---|
| 关节中位、限位、方向 | 内部 Flash 独立扇区 + 外部 Flash 备份 | 掉电保持,写入前擦除扇区 |
| 机械常数(足长等) | 编译期常量 robot_config.h | 结构变化即重新编译 |
| 黑匣子日志 | 外部 Flash 循环区 | 记录状态迁移、错误、安全事件,便于事后分析 |
| 协议统计 | RAM | 掉电不保持 |

校准数据必须是"双份加 CRC":内部 Flash 一份、外部 Flash 一份,启动时校验;任一份损坏则用另一份恢复,两份都坏则进入 FAULT 并拒绝运动。

### 3.6 开发流程(逐步,每步都要留下 log)

| 步骤 | 输入 | 成功条件 | 失败条件与动作 |
|---|---|---|---|
| 1. 环境建立 | arm-none-eabi-gcc、CMake、OpenOCD 或 ST-Link | 生成 .elf 与 .bin | 工具链缺失,记录版本后暂停 |
| 2. 复位与时钟 | 板与 8MHz 晶振 | 断点读 SystemCoreClock 为 168MHz | 起振失败则查负载电容与时钟配置 |
| 3. GPIO 与串口 | 串口工具 | 115200 收到启动横幅 | 乱码则核对波特率与时钟树 |
| 4. SPI 与 IMU | IMU 焊接 | 读 WHO_AM_I 匹配且数据合理 | ID 不对则查 SPI Mode 3 与片选 |
| 5. 单路 PWM | 示波器或舵机 | 1500us 脉宽误差小于 5us | 偏差则核对预分频与 ARR |
| 6. 舵机输出 | 6 路 PWM + 3 条总线 | 6 路 PWM 正确、12 个总线节点可单独寻址且无串扰 | 通道错位则核对定时器映射;节点错位则核对节点表 |
| 7. IK 验证 | 卷尺与角度计 | 足端位置误差小于 5mm | 超差则核对机械常数与符号约定 |
| 8. 站立与步态 | 整机 | 三足步态原地走且稳定 | 不稳则调步高、占空比、重心 |
| 9. 链路联调 | P4 或 PC | 用 robot_link_ref.py 互发双向正确 | CRC 错则查字节序与 CRC 参数 |
| 10. 安全功能 | 急停按钮 | 舵机立即断电且 PWM 关断 | 未断电则查 MOS 门与 BKIN 配置 |

顺序不可跳:第 5 步没验证就做第 6 步,18 路同时异常时无法定位。

## 4. ESP32-P4 固件架构(视觉中控)

### 4.1 组件划分

| 组件 | 职责 | 对外接口 |
|---|---|---|
| cam | 摄像头初始化、取帧、帧缓冲管理 | `cam_acquire(timeout)` 返回帧句柄;`cam_release(h)` |
| prep | crop / letterbox / 色彩转换 / 归一化 | `prep_run(frame, tensor_out)` |
| infer | 模型加载、推理、NMS、量化解析 | `infer_run(tensor) -> detections[]` |
| track | 多目标跟踪(ID 分配、丢失判定) | `track_update(dets) -> tracks[]` |
| policy | 行为状态机(跟随/巡逻/互动/待机) | `policy_step(tracks, net, audio) -> motion_intent` |
| link | 与 STM32 和 C5 的协议收发 | `link_send()`,回调注册 |
| disp | 表情与叠加框 | `disp_show(expr, tracks)` |
| audio | I2S 采集、声源方向 | `audio_get_bearing()` |
| dl_model | 模型文件与转换产物封装 | 版本与校验 |

### 4.2 数据流与线程边界(必须写清楚的三件事)

| 线程 | 阻塞点 | 队列深度 | 满时策略 |
|---|---|---|---|
| cam_task | 等帧(超时 100ms) | - | 超时即计丢失帧,重试;连续失败 10 次上报告警 |
| prep 与 infer(同线程) | 等帧队列 | 1 | 丢最旧,保最新(实时性优先) |
| policy_task | 等人脸与目标事件 | 8 | 丢最旧 |
| link_task | 等协议帧 | 16 | 安全类不丢,遥测类丢最旧 |
| disp_task | 等 VSYNC 或超时 | 1 | 丢最旧 |

推理线程与采集线程解耦,但队列深度为 1:这保证"永远处理最新帧",对应实时机器人的需求。丢帧计数必须可读出。

### 4.3 视觉任务与模型选型(2026-09-27 定案:障碍 + 跟随 + 人脸 + 手势)

| 任务 | 建议技术路线 | 算力特征 | 备注 |
|---|---|---|---|
| 障碍检测 | 轻量目标检测(障碍物/地面边界)或单目深度线索 | 中,高频 | 安全相关,优先级最高 |
| 人员检测与跟随 | 轻量人体检测 + IoU/匈牙利跟踪 | 中,高频 | 跟踪放后处理,不必上模型 |
| 人脸识别 | 人脸检测(轻量)+ 人脸特征比对(小网络) | 中低,低频(1-5Hz 足够) | 识别可降频,不需要每帧跑 |
| 手势识别 | 方案 A:检测手部 → 关键点 → 时序分类;方案 B:端到端轻量时序模型 | 高,需要连续帧 | **最大的新增算力项** |

**关键设计判断(工程推论)**:四项同时全帧率运行很可能超出 P4 的推理预算。建议采用**分级调度**:

| 频率层 | 任务 | 触发 |
|---|---|---|
| 高频(≥15fps) | 人员检测 + 障碍检测 | 每帧 |
| 中频(5fps) | 手势识别 | 检测到手且人面向机器人时 |
| 低频(1-2fps) | 人脸识别 | 有新目标进入画面时 |

这样平均算力需求接近"只需一个检测模型",而不是四个模型叠加。**这个结论必须用实验卡 EC-01/EC-07 实测验证,现在只是设计假设。**

### 4.3.1 模型槽位与切换实现(2026-09-27 决策:按阶段切换,不做并发)

**核心设计:模型常驻内存,切换靠指针交换,不做运行时加载。**

| 设计项 | 做法 | 理由 |
|---|---|---|
| 槽位数量 | 建议 2-3 个常驻槽位 | 减少 PSRAM 占用;加载模型耗时 100-500ms,运行时加载会造成可见卡顿 |
| 槽位内容 | slot0=多类检测(人+障碍),slot1=人脸,slot2=手势 | slot0 常驻,因为它是安全相关的 |
| 切换方式 | 交换槽位指针 + 重置跟踪器上下文 | 指针交换 <5ms;跟踪器重置约 20-100ms,需实测 |
| 状态上报 | 每次切换后发 `VIS_MODE_STATE`(含能力位) | STM32 据此限速,见文档 03 §4.4.1 |
| 过渡处理 | 切换后保留上一模型结果 3-5 帧做衰减 | 避免目标"突然消失"导致 policy 抖动 |
| 失败处理 | 切换超时或新模型初始化失败 → 回退到 slot0 | 绝不允许停留在"无避障"状态 |

**推荐:把"人员 + 障碍"合并为一个多类检测模型。** 跟随态需要同时看人和障碍,一个多类模型比两个模型省一次完整推理,也天然消除了"跑人检测时没跑避障"的安全缺口。

**切换延迟预算(估算,待实测)**

| 环节 | 估算耗时 |
|---|---|
| 指针交换 | <5ms |
| 跟踪器/上下文重置 | 20-100ms |
| 首帧结果产出 | 1-2 个推理周期 |
| **总计** | **约 50-150ms** |

因此 `CMD_VIS_MODE` 的 `max_switch_ms` 默认给 200ms,超过即视为失败并回退。

### 4.4 模型部署流程

| 步骤 | 输入 | 成功条件 | 失败动作 |
|---|---|---|---|
| 1. 模型选型 | 任务清单(人/人脸/障碍) | 选定 1-2 个轻量模型 | 记录候选与算力需求 |
| 2. 模型检查 | .onnx 或 .tflite | 用 inspect 工具得出算子、参数量、输入形状 | 保留完整报告 |
| 3. 转换 | ESP-DL 或官方转换工具 | 转换器返回 0 且无未支持算子 | 保存工具版本、命令、错误节点与完整 log(负面结论也要留证据) |
| 4. 精度对齐 | 同一批测试图 | 与 PC 端结果偏差在可接受范围 | 定位是量化还是前处理差异 |
| 5. 板上推理 | 板与摄像头 | 实测帧率与延迟写入实验卡 | 未达标则降分辨率或换模型,不下"不可行"结论 |
| 6. 与协议对接 | 推理输出 | VIS_TARGET 字段正确且时间戳对齐 | 核对 bearing 方向与符号 |

### 4.5 行为状态机(policy)

```
IDLE --检测到主人或唤醒词--> ACTIVE
ACTIVE --指定跟随--> FOLLOW --目标丢失 3s--> SEARCH --10s 未找到--> IDLE
ACTIVE --语音/App 指令--> ACTION --动作完成--> ACTIVE
FOLLOW --障碍物进入安全距离--> AVOID --通过--> FOLLOW
任意状态 --REMOTE_ESTOP 或本地急停--> ESTOP --人工恢复--> IDLE
任意状态 --网络与本地均无交互 5min--> SLEEP
```

policy 只产出"运动意图"交给 STM32,不直接计算关节角。所有意图都要经过限幅与安全检查。

### 4.6 资源与性能目标(基线,待实测)

| 指标 | 目标 | 备注 |
|---|---|---|
| 推理分辨率 | 720p 或 640x480 | 1080p 仅用于编码与显示 |
| 推理帧率 | ≥15fps | 低于 10fps 则跟随体验明显变差 |
| 推理延迟 | ≤30ms | 端到端预算的关键项 |
| 内存 | 帧缓冲放 PSRAM,内部 SRAM 留给栈 | 具体分区待模组确定 |
| 视频上行 | 720p H.264 1.5-4Mbit/s | 受 L3-L2 链路制约 |

### 4.7 显示与触摸组件(480×480 incell + MIPI)

| 组件 | 职责 | 备注 |
|---|---|---|
| disp_drv | MIPI-DSI 初始化、时序配置、帧刷新 | 480×480@60Hz,双缓冲 |
| disp_ui | 表情系统与 UI 图层 | 表情用动画帧或矢量绘制,避免每帧重绘整屏 |
| disp_touch | incell 触摸读取、手势解析 | I2C 读点;需要去抖与长按判定 |
| disp_backlight | 背光亮度与开关 | PWM 调光;无交互时可降亮度省电 |

**设计要求**

| 需求 | 做法 |
|---|---|
| 表情要"活" | 眼睛持续做微动画(呼吸、眨眼、注视目标方向),而不是静态图 |
| 跟随目标时的眼神 | 用 `VIS_TARGET.bearing_cdeg` 驱动瞳孔偏移,这是低成本高体验的交互 |
| 不抢推理算力 | 显示刷新放在核 0 低优先级任务,渲染用 GPU/2D 加速或缓存图层 |
| 触摸反馈要即时 | 触摸事件独立线程,直接产生事件,不等推理结果 |
| 隐私 | 背光与摄像头可分别关断,状态可见(用户知道摄像头是否在工作) |

## 5. ESP32-C5 固件架构(网络与感知)

### 5.1 组件划分

| 组件 | 职责 | 对外接口 |
|---|---|---|
| net | Wi-Fi 连接管理、802.15.4、BLE | 事件回调 + 状态查询 |
| bridge | SPI 从机收发、与 P4 的流控 | `bridge_poll()` / 回调 |
| proto | robot_link 实例(UART 与 SPI 各一) | 同 shared 协议栈 |
| cloud | MQTT/TLS 客户端、遥测上报、OTA 下载 | `cloud_publish()` / `cloud_subscribe()` |
| ota | 固件下载、校验、分发给 P4 或 STM32 | `ota_start(target)` 状态机 |
| sense | CSI 采样、存在与运动判断 | `sense_presence()` |

### 5.2 关键约束

| 约束 | 说明 |
|---|---|
| C5 是唯一持有 TLS 凭据的节点 | 凭据存于 NVS 加密分区;P4 与 STM32 不接触网络凭据 |
| C5 不直接下发运动指令 | 所有云端指令经 P4 的白名单校验后才可能变成运动意图 |
| 远程急停是唯一例外 | REMOTE_ESTOP 直接发给 STM32,只允许收紧安全状态 |
| 视频流不落盘 | 除非用户显式开启录像,避免隐私与存储风险 |
| OTA 必须支持回滚 | 双分区 + 版本校验 + 失败自动回退到旧分区 |
| 无线感知的隐私边界 | CSI 存在检测不涉及图像,但结果只用于本地行为;是否上云需用户明确同意 |

### 5.3 断网与降级行为

| 场景 | 行为 |
|---|---|
| Wi-Fi 断开 | 机器人本地功能全部保留(视觉、跟随、动作);仅云功能不可用;周期性重连并退避 |
| 云端不可达 | 遥测进入本地环形缓冲(限容量),恢复后补传最近 N 条 |
| C5 重启 | P4 检测 SPI 心跳丢失,暂停视频上行,本地功能不受影响 |
| 配网失败 | 进入配网模式(BLE 配网热点),由 App 完成配置 |

## 6. M3 电源驱动模块固件(可选,建议采用)

只有一颗小 MCU(如 STM32G030F6P6 / CH32V003),代码量很小,但职责是**全机最后一道防线**。

| 功能 | 触发 | 动作 |
|---|---|---|
| 过流保护 | 任一组电流超阈值并持续 N ms | 直接切断舵机电源 |
| 低压保护 | 母线电压低于阈值 | 切断舵机电源 + 拉低告警 |
| F407 心跳丢失 | 500ms 无心跳 | 切断舵机电源 |
| 浪涌控制 | 上电 | 软启动斜坡 + 浪涌监测 |
| 状态上报 | 周期 | 通过 I2C 或 UART 向 F407 汇报电压/电流/故障码 |

**设计铁律**

- 该 MCU **不参与运动控制**,只做保护与上报
- 切断动作走**硬件通路**(MOS 栅极),不依赖 F407
- 它自己也要有独立看门狗;它挂了同样要切舵机电源(失效安全)
- 与 F407 的接口建议只用一根 UART + 一根心跳线,简单到几乎不会出错

> 若决定不采用这颗 MCU,必须在文档 06 的验证计划里补一条"F407 死机时舵机电源如何被切断"的实验,并接受"仅靠 407 自身软件保护"的风险。

## 7. 构建、版本与烧录(草案)

### 7.1 版本号规则(三节点一致)

```
主版本.次版本.修订号 + build_id(编译时间戳或 git 短哈希)
```

协议兼容性以主版本号为准:主版本不一致则拒绝通信(见协议 NACK: E_BADVER)。

### 7.2 构建入口(待 SDK 版本确定后具体化)

| 节点 | 构建方式 | 产物 |
|---|---|---|
| STM32F407 | CMake + arm-none-eabi-gcc | .elf / .bin / .hex |
| ESP32-P4 | ESP-IDF 的 idf.py | bootloader + partition-table + app .bin |
| ESP32-C5 | ESP-IDF 的 idf.py | bootloader + partition-table + app .bin |
| shared | 被上述三者共同编译,同时可单独在 PC 上跑单元测试 | 主机测试可执行文件 |

### 7.3 烧录与复原前置条件(未满足前不执行任何写操作)

**必须先确认的复原路径:**

| 节点 | 复原入口 | 前提 |
|---|---|---|
| STM32F407 | SWD(PA13/PA14)+ BOOT0 跳线 | BOOT0 可手动置高进入系统存储器 bootloader;SWD 未被读保护关闭 |
| ESP32-P4 | USB-Serial-JTAG + 下载模式按键 | 能进入下载模式;分区表与 bootloader 可重新烧写 |
| ESP32-C5 | USB-Serial-JTAG + 下载模式按键 | 同上 |

流程(草案,默认 dry-run):

1. 确认上表中该节点的复原入口可用(实测一次擦除并恢复)
2. 记录当前固件版本与分区表(备份)
3. 编译并保留产物哈希
4. 写入前先 dry-run 或仅校验,确认端口与镜像正确
5. 写入后**读回校验**(哈希或版本读回)
6. 失败立即停止,保留完整 log,走复原流程

**硬闸门**:烧写 Option Bytes、开启读保护或 Boot 锁定、写入 secure boot 公钥、写入 flash 加密密钥、任何 OTP/eFuse 写入——只做风险评估与步骤说明,不提供可直接执行的完整命令,也不代为执行。

### 7.4 日志与证据保存约定

| 类型 | 路径 | 内容 |
|---|---|---|
| 构建日志 | `logs/<日期>-build/` | 编译器版本、完整输出、产物哈希 |
| 烧录日志 | `logs/<日期>-flash/` | 端口、镜像版本、写入与读回结果 |
| 实验数据 | `logs/<日期>-<实验名>/` | 实验卡定义的指标原始数据 |
| 板载黑匣子 | 外部 Flash 循环区 | 状态迁移与安全事件,由 log_viewer.py 解析 |
