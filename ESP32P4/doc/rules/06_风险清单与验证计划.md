### 实验卡:EC-01 ESP32-P4 视觉推理性能与算子兼容性

日期:待执行 | 对应待验证结论:EMBEDDED_CONTEXT.md §9"ESP32-P4 的 NPU 加速能力与算子兼容性"

**要消除的不确定性**

目标检测模型(人员/人脸)能否在 ESP32-P4 上以 ≥15fps、单帧推理 ≤30ms 运行。当前证据等级为"数据不足",现有公开规格无法推出实际帧率。

**前置条件**

- 环境与版本:ESP32-P4 开发板 + 官方摄像头模组;ESP-IDF 版本(需支持 P4);推理框架与其版本;PC 侧模型转换工具版本
- 输入:1-2 个候选模型(建议先取其官方示例模型,再试自训模型);一批 100 张测试图
- 前置状态:摄像头采集样例先跑通,确认能稳定取帧

**执行命令**

```
# 1. 记录工具链与 SDK 版本(必须存进 log)
# 2. 跑官方摄像头采集示例,确认取帧稳定
# 3. 用官方示例模型跑推理,记录帧率与延迟
# 4. 跑自训模型,记录转换器输出与是否有未支持算子
#    人工:若出现未支持算子,记录算子名称与所在节点后暂停,不要直接下"不可行"结论
```

**要保存的 log**

- 保存方式:`logs/2026-xx-xx-ec01-p4-infer/`
- 要记录:推理耗时(多次测量的均值/最大值)、端到端帧率、内存峰值、CPU 占用、模型文件大小、量化类型、温度
- 失败时额外保存:转换器完整输出、未支持算子清单、SDK 与工具版本

**成功 / 失败 / 停止条件**

- 成功:720p 输入下推理 ≤30ms 且整体 ≥15fps,或 640x480 下 ≥20fps 且精度可用
- 失败:最佳配置下仍 <10fps,或关键算子不支持且无替代
- 停止:出现存储损坏告警或设备反复重启,立即停止并保留 log

**结果如何改变下一步**

- 若成功:把结论升级为"已确认",冻结模型选型与分辨率,进入协议对接
- 若失败:降级方案为"P4 只跑人形检测 + 传统跟踪",或改硬件方案;开新实验卡验证降级方案
- 无论结果:把结论、证据标记、日期、log 路径写回 EMBEDDED_CONTEXT.md 第 8 节

### 实验卡:EC-02 ESP32-C5 SPI 从机吞吐

日期:待执行 | 对应风险:R2

**要消除的不确定性**

ESP32-C5 作为 SPI 从机时,在 20-40MHz 时钟下的实际可持续吞吐是多少,能否满足 720p H.264 上行所需的 1.5-4Mbit/s 加上协议开销。

**前置条件**

- 环境:ESP32-P4 与 ESP32-C5 各一块 + 杜邦线或转接板;ESP-IDF 版本
- 输入:一个持续发送伪随机数据的测试固件
- 前置状态:两侧 SPI 收发最小示例已跑通

**执行命令**

```
# 1. 先以 10MHz 跑通收发,校验数据一致
# 2. 逐步提高时钟(10/20/40MHz),每档跑 60s 计数吞吐
# 3. 加入握手线模拟真实数据流控
#    人工:观察是否有丢字节,记录每档的最高稳定速率
```

**要保存的 log**

- 保存方式:`logs/2026-xx-xx-ec02-spi-throughput/`
- 要记录:每档时钟下的实测吞吐(MB/s)、误码数、丢包数、CPU 占用
- 失败时额外保存:两侧的错误码与复位日志

**成功 / 失败 / 停止条件**

- 成功:20MHz 下可持续吞吐 ≥1MB/s 且 60s 无错误
- 失败:任何时钟下吞吐 <0.5MB/s 或误码率不可接受
- 停止:出现连续硬件错误或板子发热异常,立即停止

**结果如何改变下一步**

- 若成功:确定 SPI 时钟与流控参数,写入文档 02 与 03
- 若失败:改用 ESP-Hosted 或评估其他上行路径,重开实验卡

### 实验卡:EC-03 ESP32-C5 无线感知(CSI)可用性

当前 ESP-IDF 版本在 ESP32-C5 上是否提供 CSI 数据获取接口,采样率与数据量是否足以判断"有人存在/移动"。

**前置条件**

- 输入:CSI 采集固件、简单的静止/走动测试脚本
- 前置状态:能连上 AP 并维持稳定连接

**执行命令**

```
# 1. 查 ESP-IDF 文档确认 C5 的 CSI API 是否存在与支持频段
# 2. 跑 CSI 采集,连续采 5 分钟,场景:无人静止 / 有人静止 / 有人走动
# 3. 记录原始 CSI 幅度与相位数据,做简单统计或阈值判断
#    人工:每个场景至少重复 3 次,避免单次偶然
```

**要保存的 log**

- 保存方式:`logs/2026-xx-xx-ec03-csi/`
- 要记录:每种场景的 CSI 采样率、数据长度、区分度指标(如方差)

- 成功:三种场景能被简单阈值或轻量分类器区分,误判率可接受

**结果如何改变下一步**

- 若成功:确定 CSI 采样参数与判断算法,进入 C5 固件设计
- 若失败:该功能降级为"仅做 Wi-Fi/BLE 连接与信道评估",不承诺存在感知

### 实验卡:EC-04 MG996R 电流、扭矩与电源能力验证

日期:待执行 | 对应风险:R4、R7、R13、R16

**要消除的不确定性**

三件事必须一起测,因为它们互相耦合:

1. 单台 MG996R 的**空载、保持(受力静止)、运动、堵转**电流分别是多少
2. 18 台同时上电与同时运动时,**母线跌落**是否会让 MCU 或舵机异常
3. 实测扭矩是否接近规格书的 11 kg·cm,以及整机质量是否真的控制在 2.2kg 内

现在文档 07 §6 的扭矩余量只有约 1.0(估算),本实验是把"估算"升级为"已确认"的唯一途径。

**前置条件**

- 环境:MG996R 至少 3 台(建议来自不同批次,个体差异大);可测电流的电源(或库仑计/分流 + 示波器);示波器观察母线电压;扭力计或砝码杠杆(测扭矩)
- 输入:MG996R 规格书;文档 07 §6 的扭矩估算表
- 前置状态:能产生 50Hz、500-2500µs 的稳定 PWM(可用 F407 或舵机测试仪)

**执行命令**

```
# 1. 单台空载:500us/1500us/2500us 三个位置各停 10s,记录电流
# 2. 单台保持:加 50% 额定扭矩的砝码,保持 30s,记录稳态电流(这是最容易被低估的一项)
# 3. 单台运动:往复扫 30° ,记录电流波形与启动瞬间峰值
# 4. 单台堵转:输出与机械限位相反的脉宽,持续 2s 即停,记录峰值电流与温升
#    人工:第 4 步若舵机外壳明显发热或有异味,立即停止并冷却后再继续
# 5. 6 台同组同时启动,记录母线跌落
# 6. 18 台上电浪涌:重复上电 10 次,用示波器抓母线跌落与恢复时间
# 7. 扭矩实测:杠杆 + 砝码,测量 6V 下的实际保持扭矩
#    人工:与规格书 11 kg·cm 对比,偏差超过 20% 要记录批次
```

**要保存的 log**

- 保存方式:`logs/2026-xx-xx-ec04-servo-current/`
- 要记录:空载/保持/运动/堵转四态电流(峰值与平均)、18 台浪涌峰值、母线跌落幅度与恢复时间、实测扭矩、舵机批次号、温升
- 失败时额外保存:舵机或电源异常的证据(照片、波形截图)

**成功 / 失败 / 停止条件**

- 成功:保持电流实测值使 18 台稳态总电流 ≤6A;母线跌落 <5% 且 MCU 不复位;实测扭矩 ≥9 kg·cm
- 失败:18 台稳态总电流 >10A,或跌落导致 MCU 复位,或实测扭矩 <8 kg·cm
- 停止:出现冒烟、异味、烫手立即停止;堵转测试单次不超过 2s

**结果如何改变下一步**

- 若成功:冻结保险丝、线径、母线电容参数与续航预期,更新文档 01/02/07;**并把扭矩余量从"估算"升级为"已确认"**
- 若失败且是电流问题:提高母线电容、分组错时启动、或改用更高效率的舵机降压
- 若失败且是扭矩问题:这是 R13 触发,必须走两条路之一——整机减重到 1.5kg 以下,或把大腿关节换成 20-25 kg·cm 的数字舵机(引脚兼容,升级预留已就绪)

日期:待执行 | 对应风险:R5、R8、R11

三条链路在真实噪声环境(舵机同时工作)下能否长时间无错;时间同步的漂移是否在可接受范围。

**前置条件**

- 环境:三节点全部上电,固件含协议栈与统计计数;舵机处于工作状态以引入真实噪声
- 输入:协议一致性测试工具 `tools/robot_link_ref.py`
- 前置状态:协议单向收发已跑通

**执行命令**

```
# 1. 双向持续收发 1 小时,记录统计计数
# 2. 让舵机以各种步态工作,重复第 1 步
# 3. 观察每 5s 一次的 TIME_SYNC,记录 offset 与 delay 的分布
# 4. 拔插线缆 20 次,验证链路自恢复
#    人工:任何一次测试出现计数异常增长就停止,保留现场
```

**要保存的 log**

- 保存方式:`logs/2026-xx-xx-ec05-link-longrun/`
- 要记录:crc_errors / len_errors / drops / retries / rx_frames 计数;offset 与 delay 分布;拔插后的恢复时间
- 失败时额外保存:故障瞬间两侧的完整统计与时间戳

**成功 / 失败 / 停止条件**

- 成功:1 小时 0 CRC 错误、0 长度错误;拔插后 500ms 内恢复;offset 抖动 < 1ms
- 失败:出现持续错误增长或链路无法自恢复
- 停止:出现设备复位或死机,立即停止并保存两个节点的状态快照

**结果如何改变下一步**

- 若成功:链路方案冻结,协议统计写入遥测
- 若失败:根据错误类型选择提高校验、降低速率、改为差分物理层或换总线

### 实验卡:EC-10 模型切换的安全缺口验证

日期:待执行 | 对应风险:R19 | 依赖:EC-07 完成

**要消除的不确定性**

当 P4 切到不含障碍检测的模式时,STM32 是否真的按能力位强制限速;切换失败、状态丢失、P4 死机这三种情况下,机器人是否停在安全状态。当前这条规则只写在文档里,没有任何实现验证。

**前置条件**

- 环境:三节点完整系统,固件含能力位协商(`CMD_VIS_MODE` / `VIS_MODE_STATE`);能人为制造切换失败
- 输入:文档 03 §4.4.1 的规则表;可观测的速度上限与实际速度日志
- 前置状态:跟随功能可用,速度指令可被记录

**执行命令**

```
# 1. 跟随中发出"切到仅手势模式"的请求,检查 STM32 是否限速
# 2. 人为让 P4 不回 VIS_MODE_STATE(例如屏蔽该消息),检查超时后的行为
# 3. 让 P4 上报 caps=0,检查速度上限是否立即收紧
# 4. 拔掉 M1 电源模拟 P4 死机,检查机器人是否收腿并停下
# 5. 重复上面 1-4 各 10 次,统计是否每次都进入安全状态
#    人工:每次都要记录"实际速度"而不只是"是否停下"
```

**要保存的 log**

- 保存方式:`logs/2026-xx-xx-ec10-mode-safety/`
- 要记录:每次请求的 caps 值、STM32 生效的速度上限、实际最大速度、进入安全状态的耗时
- 失败时额外保存:那一时刻的双向报文原始记录

**成功 / 失败 / 停止条件**

- 成功:40 次测试全部进入安全状态;caps=0 时实际速度不超过设定上限
- 失败:出现任何一次"caps 为 0 但机器人仍按正常速度运动"
- 停止:发现机器人朝障碍物或人加速,立即急停并停止测试

**结果如何改变下一步**

- 若成功:R19 关闭,能力位机制可作为安全设计定稿
- 若失败:必须改为**强制方案**——由 STM32 维护"允许的运动包络",P4 只能在其中申请,而不是上报能力让 STM32 被动响应

### 实验卡:EC-11 总线舵机故障注入与降级

- 若失败:改进方向为"每条总线独立任务 + 硬超时 + 单总线失效即静止收腿",或改为每腿一条总线(成本上升)
