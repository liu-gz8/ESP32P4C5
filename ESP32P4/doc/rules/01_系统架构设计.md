## 1. 设计目标与约束

### 1.1 产品定位

六足(3 DOF × 6 足 = 18 关节)陪伴机器人,具备:

- **运动**:全向行走、转向、蹲坐、姿态调整、温顺动作表达(招手/点头/跳舞)
- **视觉**:人员检测与跟随、人脸识别、障碍物检测、表情交互
- **听觉**:麦克风阵列声源方向估计(可选,取决于是否装阵列)
- **连接**:手机 App / 云端连接、远程遥测、OTA、无线存在感知
- **安全**:硬件急停、通信失联保护、舵机电源硬切断

### 1.2 硬性约束(不可退让项)

| 约束 | 目标值 | 说明 |
|---|---|---|
| 安全响应 | 急停 → 舵机断电 ≤ 10ms | 硬件路径,不依赖软件链路 |
| 通信失联保护 | 主链路丢失 200ms → 进入安全姿态 | 由 STM32 独立判定,不依赖 P4 |
| 控制回路 | IMU 1kHz,运动解算 ≥250Hz,舵机更新 ≥50Hz | 由 STM32 保证 |
| 端到端视觉到动作 | ≤150ms(基线目标) | 含曝光、推理、链路、解算 |
| 单点故障隔离 | M1 感知模块死机不得导致机器人摔倒 | P4 失联时 F407 自主保持或收腿 |

### 1.3 为什么是三个 MCU(架构理由)

| 需求 | 为什么不能只用一个 | 分工 |
|---|---|---|
| 18 路硬实时 PWM + 1kHz IMU 闭环 | 视觉推理的调度抖动会直接破坏舵机时序 | STM32F407 独占实时域 |
| 1080p 视觉管线 + AI 推理 | M4F 算力不足;P4 的 ISP、2D-DMA、H.264 是视觉专用硬件 | ESP32-P4 独占视觉域 |
| Wi-Fi 6 双频 + 802.15.4 + 无线感知 | P4 没有集成射频(已确认,待核对 datasheet 版本) | ESP32-C5 独占网络域 |

**核心架构原则:每个域只有一个权威节点,跨域只传语义,不传控制细节。**

## 2. 分层与职责划分

### 2.1 三层节点模型

```
┌──────────────────────────────────────────────────────────────┐
│  L3 意图层 / 云与用户                    [ESP32-C5]           │
│  · 唯一 IP 边界(TLS / MQTT / HTTPS)                          │
│  · 手机 App 指令、云端遥测、OTA 管理                           │
│  · 无线感知:Wi-Fi CSI 存在检测、BLE 扫描、信道评估            │
│  · 远程急停(最高优先级的旁路通道)                            │
└────────────┬─────────────────────────────────┬───────────────┘
             │ SPI 20-40MHz + 握手线            │ UART 921600
             │ (数据面:视频/遥测/指令)          │ (管理/安全旁路)
┌────────────▼──────────────────┐   ┌──────────▼───────────────┐
│  L2 感知决策层       [ESP32-P4]│   │  L1 运动安全层 [STM32F407]│
│  · MIPI-CSI 摄像头 + ISP       │   │  · 6 路 PWM + 3 条总线舵机 │
│  · AI 推理(人/人脸/障碍)      │   │  · 1kHz IMU 姿态闭环      │
│  · 目标跟踪、行为状态机        │◄──┤  · 逆运动学 + 步态引擎    │
│  · H.264 编码、表情显示        │UART│  · 电源管理、硬件急停     │
│  · 声源方向估计(I2S)          │3Mb │  · 失联保护(自主兜底)    │
└───────────────────────────────┘   └──────────────────────────┘
```

### 2.2 权威边界(避免多头指挥)

| 决策内容 | 唯一权威 | 其他节点只能 |
|---|---|---|
| 关节角度、步态相位、PWM 输出 | STM32F407 | 请求,不能直接写 |
| 是否允许运动(安全门) | STM32F407 | 请求解除,不能强令 |
| 去哪里、跟谁、做什么动作 | ESP32-P4 | 提出目标,不能指定关节 |
| IP 地址、TLS 凭据、云端会话 | ESP32-C5 | 无 |
| 系统时间基准 | STM32F407 | 对齐自身时钟 |

**关键规则**:C5 在任何情况下都不直接下发运动指令。C5 只能下发 `REMOTE_ESTOP`(只允许收紧安全状态)和 `CLOUD_CMD`(由 P4 或 STM32 二次校验后执行)。

### 2.4 物理模块划分(2026-09-27 决策落地)

逻辑分层与物理模块是两回事:逻辑上分三层(M1/M2 与 M3 的职责交叉),物理上分三块板。

| 物理模块 | 承载的逻辑角色 | 说明 |
|---|---|---|
| M1 感知模块 | L2(视觉)+ L3(网络) | **P4 与 C5 同板**,P4↔C5 走板内 SPI,不跨板 |
| M2 控制模块 | L1(运动安全) | STM32F407 + IMU + 外部 Flash |
| M3 电源驱动模块 | 供电与驱动 | 电池、软启动、6V/25A 舵机降压、PWM 缓冲、分组电流采样、18 路舵机插座 |

两个直接后果:

1. **P4↔C5 的 SPI 变成板内短线**,信号完整性最好,可以做 40MHz
2. **6 路 PWM 与 3 条总线必须跨板送到 M3**(第二次调整后),M2↔M3 连接器约 34-36 pin,并在 M3 上做 5V 缓冲与半双工总线转接——顺带获得了对 MCU 引脚的保护

详细模块划分、连接器与线束见文档 07。

### 2.3 指令优先级仲裁(在 STM32 内实现)

```
优先级 0(最高): 硬件急停 / REMOTE_ESTOP       -> 立即 PWM 关断 + 舵机电源切断
优先级 1:        本地安全(IMU 倾角超限、过流、低压) -> 强制收腿/坐姿
优先级 2:        链路超时保护(200ms 无心跳)          -> 保持安全姿态
优先级 3:        P4 运动意图(速度/姿态/动作)
优先级 4:        本地行为(自检、待机摆动、低电量提示)
```

高优先级指令**抢占**低优先级,且低优先级恢复需要显式 `clear`。仲裁状态机见文档 03 第 6 节。

## 3. 数据流设计

设计规则:每一段必须回答 **buffer 从哪来、能否 zero-copy、跑在哪条任务**。

### 3.1 视觉数据流(ESP32-P4 内部)

| 段 | buffer 策略 | zero-copy 机会 | 任务归属 | 证据 |
|---|---|---|---|---|
| 采集(MIPI-CSI) | 驱动侧帧环,建议 3 缓冲;1080p YUV422 单帧约 4MB | 确认 P4 ISP 能否直接输出到 PSRAM 帧缓冲 | cam_task(核 1,阻塞等帧) | 待验证 |
| 前处理(crop / letterbox / RGB) | 优先 ISP / PPA 硬件;CPU 做则需独立缓冲 | ISP 加 PPA 链路可省整段 | 并入 prep 阶段 | 待验证 |
| 推理 | 模型输入 tensor;优先让前处理输出直接作输入 | 支持外部内存输入则省一次拷贝 | infer_task(核 1,队列深度 1) | 待验证 |
| 后处理 / NMS | 输出 tensor 很小,允许拷贝 | 低优先 | 并入 infer 阶段 | 工程推论 |
| 跟踪 / 行为决策 | 结构化结果(几 KB) | 不适用 | policy_task(核 0) | 工程推论 |
| 显示叠加 | 复用帧缓冲做 overlay | 叠加框而非重绘整帧 | disp_task | 工程推论 |
| 编码 / 上行 | H.264 码流环形缓冲(固定 256KB) | 硬件编码器输出直接入环 | stream_task | 待验证 |

**带宽账(估算)**:1080p@30fps YUV422 原始流约 3.7 Gbit/s,必须靠 ISP 直接写 PSRAM 且全程避免 CPU 拷贝;若发生一次 CPU 拷贝,单帧 4MB × 30fps = 120MB/s,会吃掉大部分内存带宽预算。因此基线选择 **720p 用于推理,1080p 仅用于编码或显示**。

### 3.2 控制数据流(STM32F407 内部)

| 段 | 频率 | buffer 策略 | 任务 | 阻塞点 |
|---|---|---|---|---|
| IMU 采样(SPI + DRDY 中断) | 1000Hz | 双缓冲乒乓,每块 1 帧 | imu_task | 阻塞等 DRDY 信号量 |
| 姿态解算(互补 / Mahony) | 1000Hz | 无缓冲,原地计算 | imu_task | 无 |
| 运动意图接收(链路) | 事件驱动 | 环形 RX 缓冲 4KB + 消息队列深度 8 | comm_task | 阻塞等 DMA 空闲中断 |
| 逆运动学(18 关节) | 250Hz | 输入输出各一结构体,无动态分配 | gait_task | 无(周期任务) |
| 舵机 PWM 更新 | 50Hz | 影子寄存器 | gait_task | 无 |
| 电源监测(ADC + INA226) | 100Hz | 8 点滑窗 | power_task | 无 |
| 健康监控 / 看门狗 | 10Hz | 无 | supervisor_task | 无 |

**关键设计**:链路接收与运动解算**解耦**。comm_task 只做解码,把语义写入意图信箱(单写单读,带版本号);gait_task 每个周期读最新意图并做限幅和斜率限制。这样即使链路突发大量数据,也不会破坏 PWM 时序。

### 3.3 端到端延迟预算(估算,待验证)

| 环节 | 目标 | 备注 |
|---|---|---|
| 曝光 + 读出(720p@30) | 33ms | 上限由帧率决定 |
| ISP + 前处理 | 5-10ms | 硬件路径 |
| 推理 | 15-30ms | 最大不确定项,待实测 |
| 后处理 + 组帧 | ≤2ms | |
| P4 到 STM32 链路(64B @3Mbps) | <1ms | |
| STM32 解析 + 仲裁 | ≤1ms | |
| IK 解算到下一次 PWM 生效 | ≤20ms | 50Hz 更新周期 |
| **合计** | **约 60-100ms** | 达标(≤150ms),但依赖推理耗时实测 |

控制侧闭环(IMU 到舵机)延迟:IMU 采样 1ms + 解算 0.5ms + 舵机更新 ≤20ms,合计约 22ms,对姿态稳定足够。

## 4. 链路拓扑与选择理由

### 4.1 三条链路

| 链路 | 物理层 | 速率 | 用途 | 理由 |
|---|---|---|---|---|
| L2-L1 | UART + DMA(STM32 USART1 对 P4 UART1) | 3 Mbit/s | 运动意图、关节遥测、时间同步、日志 | 带宽需求低于 100kB/s,无需时钟同步,双方 DMA 成熟,调试器可直接抓 |
| L3-L1 | UART(STM32 USART3 对 C5 UART) | 921.6 kbit/s | 管理旁路:遥测上报、OTA 透传、远程急停、STM32 复位 | 即使 P4 死机,C5 仍能救回 STM32 并上报云端 |
| L3-L2 | SPI(P4 主机对 C5 从机)+ 2 根握手 GPIO | 20-40 MHz | 视频/音频流上行、网络事件下发、遥测代理 | 视频回传需 ≥2MB/s;SPI 从机在 C5 上为硬件外设,负载低 |

### 4.2 为什么 L3-L2 不首选 ESP-Hosted

ESP-Hosted 能让 P4 直接拿到标准 sockets,但代价是 P4 上多一套 IP/TLS 栈、双份凭据与 OTA 逻辑、故障面更大。

基线选型:C5 作为唯一 IP 边界,自定义二进制协议;P4 只发结构化事件和码流。

- 优点:单一 TLS / 凭据 / OTA 边界;P4 省 CPU 与 RAM;攻击面更小
- 代价:多一跳(P4 → C5 → Wi-Fi),估算额外 10-20ms;P4 无法直接跑 WebRTC
- 退路(待验证):若实测本地视频延迟超过 200ms,改为 ESP-Hosted(需先确认其对 P4 + C5 组合的支持)

### 4.3 时间同步

- **主时钟**:STM32F407 的 1ms 系统节拍(由 HSE 8MHz + PLL 派生,精度约 ±30ppm,估算)
- **同步机制**:NTP 式四时间戳(TIME_SYNC_REQ / TIME_SYNC_RESP),由 STM32 发起
- **周期**:启动后一次,之后每 5s 一次;P4 与 C5 维护 offset 和 drift
- **对外时间戳**:所有跨节点事件携带 ts_ms(u32,**STM32 时基**),P4 在发送前换算
- **失效处理**:连续 3 次同步失败,该节点时间戳标记为本地时基,接收方按不可跨节点比较处理

## 5. 电源与电气架构

### 5.1 电源树

```
 3S LiPo (9.0-12.6V, 3000-5000mAh, >=30C)   [全部集中在 M3 电源驱动模块]
   |
   +--[主保险丝 25-30A]--[软启动限流 + 主开关 MOS]--+-- SRV_PWM 降压 6.0-6.5V / 10-12A
   |                                                |     +-- 6x MG996R(小腿)
   |                                                |     +-- 2x INA226
   |                                                |
   |                                                +-- SRV_BUS 6-8.4V 或 12V(按型号)/ 15-20A
   |                                                |     +-- 12x 总线舵机(髋 + 大腿,BUS_A/B/C 三条)
   |                                                |     +-- 3x INA226
   |                                                |     +-- 每轨 >=2200uF 低 ESR 母线电容
   |                                                |     +--[舵机使能 MOS, PE3 经 M3 门控]
   |                                                |
   |                                                +--[Buck 5V/4A]-- 5V_AUX(π 型滤波)
   |                                                                      +-- J3 --> M1: 本地 3V3/1V8/2V8 + 背光升压
   |                                                                      +-- J2 --> M2: 本地 3V3
   |
   +--[急停回路:常闭按钮 + 遥控 MOS 门]-- 硬件串联在舵机使能路径(不经 MCU)
                                          + (可选)独立监督 MCU 直接切断舵机电源
```

### 5.2 电源设计要点

| 要点 | 做法 | 理由 |
|---|---|---|
| 数字域与舵机域分离 | M3 出两路独立降压;M1/M2 各自再做本地 3.3V,星形接地单点汇流 | 舵机换向尖峰会拉垮 MCU 供电并导致复位 |
| 母线储能 | 舵机母线 ≥4700uF 低 ESR + 每舵机 100nF | 18 台 MG996R 的启动浪涌(估算峰值 8-25A) |
| 软启动 | 主 MOS 斜坡启动或 NTC 旁路 | 4700uF 在 12.6V 的浪涌能量约 0.37J,无限流会触发电池保护 |
| 电源时序 | 5V_AUX → M2 → M1 → STM32 就绪后才释放舵机使能 | 避免上电瞬间舵机乱跳 |
| 急停走硬件路径 | 急停串联舵机使能 MOS,同时接 TIM1_BKIN / TIM8_BKIN | 软件死机也能切断;BKIN 直接把 PWM 置安全态 |
| 独立监督(可选) | M3 上加小 MCU,直接监测电流并切断舵机电源 | F407 跑飞时软件保护全失效,只有独立监督有效 |
| 掉电检测 | ADC + INA226 监测 VBAT,低压阈值触发主动收腿 | 避免低压下舵机失控 |

### 5.3 电流预算(MG996R,估算,待实测)

| 域 | 空闲/保持 | 典型运动 | 峰值 |
|---|---|---|---|
| 6x MG996R(小腿,PWM 轨) | 1.5-2.5A | 3-5A | 6-8A |
| 12x 总线舵机(髋+大腿,总线轨) | 3-5A | 5-9A | 10-15A |
| ESP32-P4 + 摄像头 + 480x480 屏 | 0.6A@5V | 0.9A@5V | 1.3A@5V |
| ESP32-C5 | 0.08A@3V3 | 0.25A@3V3(TX) | 0.35A@3V3 |
| STM32F407 | 0.06A@3V3 | 0.06A@3V3 | 0.07A@3V3 |

续航(估算,3S 4000mAh 约 44Wh):站立保持约 55-85min;正常行走约 30-50min;快速行走约 20-30min。

**注意**:MG996R 受力时的保持电流可达 300-500mA/个;总线舵机的保持电流取决于型号与力矩设定。两者都必须实测(EC-04),它同时决定保险丝、线径与续航。

## 6. 软件架构总览

### 6.1 分层(三个节点共用同一套分层原则)

```
应用层 Application      行为状态机、步态策略、云业务
   ↓ (只依赖接口)
服务层 Service          步态引擎、IK、姿态控制、跟踪、OTA、会话管理
   ↓
协议层 Protocol         robot_link 编解码(纯逻辑,可 PC 单测)
   ↓
驱动抽象 Driver Iface   imu_t / servo_bus_t / camera_t / net_port_t
   ↓
厂商适配 Vendor Adapter STM32 HAL/LL、ESP-IDF 驱动
   ↓
BSP / 板级              引脚映射、时钟、电源时序、外设实例
```

**铁律**:协议层与核心算法层不得包含任何厂商 HAL 头文件,这样协议与 IK 可在 PC 上单元测试。

### 6.2 各节点任务表

**STM32F407(FreeRTOS)**

| 任务 | 优先级 | 周期/触发 | 栈 | 说明 |
|---|---|---|---|---|
| gait_task | 高(4) | 4ms(250Hz) | 2KB | IK + 步态相位 + PWM 影子寄存器 |
| imu_task | 高(4) | 1ms(DRDY) | 1.5KB | 采样 + 姿态解算 |
| comm_task | 中(3) | DMA 事件 | 2KB | 双链路解码,写意图信箱 |
| power_task | 中(2) | 10ms | 1KB | ADC / INA226、电量模型 |
| supervisor_task | 低(1) | 100ms | 1KB | 健康计数、看门狗喂狗决策 |

**ESP32-P4(ESP-IDF)**

| 任务 | 核 | 优先级 | 说明 |
|---|---|---|---|
| cam_task | 1 | 高 | 阻塞取帧,丢帧策略为丢最旧保最新 |
| infer_task | 1 | 高 | 队列深度 1,推理 + NMS |
| policy_task | 0 | 中 | 跟踪与行为状态机,产出运动意图 |
| link_task | 0 | 中 | 与 STM32 / C5 的协议收发 |
| disp_task | 0 | 低 | 表情与叠加框 |
| audio_task | 0 | 中 | I2S 采集 + 声源方向 |

**ESP32-C5**

| 任务 | 优先级 | 说明 |
|---|---|---|
| net_task | 高 | Wi-Fi / BLE / 802.15.4 事件循环 |
| bridge_task | 中 | SPI 从机与协议转换 |
| sense_task | 低 | CSI 采样与存在判断 |
| cloud_task | 中 | MQTT / TLS 客户端、OTA |

### 6.3 资源预算(估算)

| 节点 | RAM 预算 | Flash / 代码 |
|---|---|---|
| STM32F407 | RTOS 10KB + 任务栈 7.5KB + 协议链路 6.6KB(实测 `rl_link_t` = 3312 B × 2 条)+ 数据 6KB 约 30KB / 192KB | 应用约 250KB / 1MB |
| ESP32-P4 | 帧缓冲放 PSRAM(≥6MB);内部 SRAM 留给栈与模型,待实测 | 模型 + 应用,分区待定 |
| ESP32-C5 | 网络栈 + 协议约 150KB,待查 datasheet 确认可用 SRAM | 需双 OTA 分区 |

### 6.4 视觉模型分级与能力协商(2026-09-27 决策)

**不分四任务并发,按行为阶段切换模型。** 这解决了算力叠加问题,但引入了新的安全约束。

| policy 状态 | 活动模型 | 建议频率 | 理由 |
|---|---|---|---|
| SLEEP / IDLE | 人脸检测 + 手势(低频) | 1-5fps | 低功耗等待交互;机器人静止,无碰撞风险 |
| ACTIVE | 人员检测 + 人脸 | 10fps | 准备交互 |
| **FOLLOW** | **人员检测 + 障碍检测** | ≥15fps | 移动中安全优先,手势关闭 |
| PATROL | 障碍检测 + 人员检测(低频) | ≥15fps | 同上 |
| INTERACT(静止) | 手势 + 人脸 | 10fps | 静止时算力让给交互 |

**关键设计:用能力位(bitmask)而不是模式名做接口。** STM32 关心的不是"P4 在哪个模式",而是"现在有哪些安全相关的感知在运行":

| 能力位 | 含义 | STM32 的行为 |
|---|---|---|
| bit0 OBSTACLE | 障碍检测运行中 | 允许按正常速度上限行走 |
| bit1 PERSON | 人员检测运行中 | 允许跟随 |
| bit2 FACE | 人脸识别运行中 | 允许身份相关动作 |
| bit3 GESTURE | 手势识别运行中 | 允许手势交互 |

**硬性安全规则**:当 bit0(障碍检测)为 0 时,STM32 必须限制速度上限(或要求机体静止)。也就是说——**P4 可以为了省算力关掉手势,但不能在移动中关掉障碍检测**。这条规则由 STM32 侧强制执行,P4 只上报能力,P4 无法绕过。

工程约束:

- 模型**常驻内存靠指针切换**,不要运行时从 Flash 加载(会有 100-500ms 卡顿)
- 建议把"人员 + 障碍"合并成**一个多类检测模型**,避免跟随态下跑两个模型
- 切换要原子,并保留几帧上一结果做衰减,避免目标突然消失导致状态机抖动

## 7. 安全设计(最高优先)

### 7.1 三层安全网

| 层 | 触发 | 动作 | 响应时间 |
|---|---|---|---|
| 硬件 | 急停按钮 / 遥控急停门 | 舵机电源切断 + TIM1/8 BKIN 关断 PWM | <10ms(硬件,估算) |
| 固件本地 | IMU 倾角 >45°、过流、低压、看门狗 | 停止运动,收腿,断电 | 20-200ms |
| 分布式 | 主链路心跳丢失 200ms | 保持当前姿态;可配置为收腿 | 200ms |

### 7.2 失联矩阵(谁死了会怎样)

| 故障 | 检测方 | 系统行为 |
|---|---|---|
| P4 死机或重启 | STM32(主链路心跳) | 保持站立或收腿;C5 上报云端;C5 可对 P4 硬复位 |
| C5 死机 | P4(SPI 心跳)与 STM32(C5 链路心跳) | 机器人本地功能不受影响;P4 停止视频上行;STM32 保留本地安全 |
| STM32 死机 | P4 与 C5 心跳 + 看门狗 | 看门狗复位;若连续复位,C5 上报并保持舵机断电 |
| 全系统掉电 | 低压检测 | 提前收腿,母线电容支撑动作收尾 |

### 7.3 本项目适用的硬闸门

以下操作**只写步骤与风险,不提供可直接执行的完整命令**:烧写 Option Bytes、开启读保护或 Boot 锁定、写入 secure boot 公钥、flash 加密密钥、任何 OTP / eFuse 写入。

任何烧录动作默认 dry-run,实际写入需明确确认,并在写入后读回校验。

## 8. 机械与运动概要

详细见文档 05。架构级要点:

- 机体六边形,六足按 60° 间隔均布(起始角以机械为准,详见文档 05),每足 3 关节:**髋偏转(coxa)、大腿(femur)、小腿(tibia)**
- 默认步态:**三足步态**(快,3+3)、**波动步态**(慢,稳定,单足摆动)、**自适应**(按 IMU 与足底接触调整)
- 运动接口:上层只给 **(vx, vy, ωz, 机体高度, 姿态角, 步高)**,不指定关节角
- 全向运动:通过足端轨迹在机体坐标系的合成实现,不需要额外转向机构

**舵机方案与硬约束(2026-09-27 第二次改版:髋+大腿走总线,小腿走 PWM)**

| 关节 | 舵机 | 扭矩 | 反馈 |
|---|---|---|---|
| 髋 coxa + 大腿 femur(12 个) | 总线舵机(25 kg·cm 级) | 2.45 N·m | 位置、力矩、温度均可读 |
| 小腿 tibia(6 个) | MG996R | 1.08 N·m @6V | **无位置反馈**,精度依赖标定表 |

| 约束 | 数值 | 依据 |
|---|---|---|
| 整机质量上限(余量 1.3,小腿决定) | **约 2.5kg** | 文档 08 §4.1 |
| 结构设计目标 | **≤2.2kg** | 基线估算 2.27-2.47kg,需留机械余量 |
| 小腿角度不确定度(不加传感器) | 1-3° → 足端 2-5mm | 估算,需 EC-09 实测 |
| 可接受的步态激进度 | 温和,限制加减速度 | 小腿仍是 MG996R |

结论:**换总线舵机把质量上限从 1.7kg 抬到约 2.5kg**,但基线估算已到 2.47kg,减重仍是必答题。小腿是新的薄弱环节,其位置精度问题见文档 08 的专项分析。

## 10. 最高影响风险(摘要)

完整清单见文档 06。最高影响的三条:

1. **ESP32-P4 的 AI 推理能力边界未知(数据不足)** — 若 P4 无专用 NPU 或算子支持差,720p 人员检测可能只有 5-10fps,直接破坏 ≤150ms 端到端目标。必须先做模型部署实验卡。
2. **ESP32-C5 的 SPI 从机与 CSI 能力待验证** — 若 SPI 从机吞吐不足,视频上行方案要改成其他路径或改用 ESP-Hosted。
3. **舵机峰值电流未知(数据不足)** — 影响保险丝、线径、电源板设计,是打样前必须冻结的参数。
4. **小腿是新的扭矩薄弱环节(估算)** — 换总线舵机后瓶颈从大腿转移到小腿(MG996R),整机上限约 2.5kg。缓解:质量 ≤2.2kg;或小腿加编码器/换总线(见文档 08)。
5. **小腿位置不可直接观测(工程推论)** — MG996R 无位置反馈,精度依赖标定表;模型无法替代位置传感器。缓解与验证见文档 08 与 EC-09。
6. **视觉模型切换的安全缺口(工程推论)** — 若在移动中切到无避障的模型会出安全事故。缓解:能力位协商 + STM32 强制限速(§6.4),验证见 EC-10。
7. **总线是新的单点故障源(工程推论)** — 一条总线故障影响 2 条腿。缓解:拆 3 条总线 + 超时可恢复 + 故障腿姿态降级,验证见 EC-11。
