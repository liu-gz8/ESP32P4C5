# 03 通信协议规范 — robot_link v1

版本:v0.1(草案)
日期:2026-09-27
适用范围:STM32F407 ↔ ESP32-P4、STM32F407 ↔ ESP32-C5、ESP32-P4 ↔ ESP32-C5
参考实现:`outputs/include/robot_link.h`(C 头文件)、`outputs/tools/robot_link_ref.py`(参考编解码与自测)

---

## 1. 设计目标

| 目标 | 做法 |
|---|---|
| 二进制高效 | 定长小端结构,无文本解析开销 |
| 抗噪声、可自恢复 | COBS 成帧 + CRC16 校验,不依赖字节间隔 |
| 资源可控 | 最大帧长固定,接收缓冲可静态分配,无动态内存 |
| 跨节点一致 | 三条链路共用同一帧格式,只换传输层 |
| 可调试 | 每条帧带 seq 与 msg_id,可打点;附 PC 侧解析脚本 |

## 2. 帧格式

### 2.1 成帧方式:COBS + 0x00 分界

```
发送:
  [header 10B][payload NB][crc16 2B]  --COBS 编码-->  [encoded][0x00]

接收:
  以 0x00 为分隔符切分 -> 对片段做 COBS 解码 -> 校验长度与 CRC16
```

选 COBS 而非固定头 + 转义的原因:

- 0x00 在有效载荷内被完全消除,分界不会误判,无需逐字节转义状态机
- 编解码是纯函数,可在 PC 上单元测试
- 开销极小:每 254 字节最多加 1 字节

### 2.2 头部字段(编码前的明文,共 10 字节)

| 偏移 | 字段 | 类型 | 说明 |
|---|---|---|---|
| 0 | ver | u8 | 协议版本,当前 `0x01`;不符则丢弃并回 `NACK(EBADVER)` |
| 1 | type | u8 | 见 2.3 |
| 2 | flags | u8 | 见 2.4 |
| 3 | src | u8 | 源 Node ID |
| 4 | dst | u8 | 目的 Node ID,`0xFF` 为广播 |
| 5-6 | msg_id | u16 LE | 消息编号,见第 4 节 |
| 7 | seq | u8 | 序号,每节点独立递增,回绕 |
| 8-9 | len | u16 LE | payload 字节数,0 表示无载荷 |

### 2.3 type 定义

| 值 | 名称 | 语义 | 是否需要 ACK |
|---|---|---|---|
| 0x01 | REQ | 请求,期望有应答 | 是 |
| 0x02 | RESP | 对应某条 REQ 的应答 | 否 |
| 0x03 | EVENT | 单向事件,不期望应答 | 否 |
| 0x04 | STREAM | 流式数据(视频/音频分片) | 否 |

### 2.4 flags 位定义

| 位 | 名称 | 说明 |
|---|---|---|
| bit0 | ACK_REQ | 要求接收方回 ACK |
| bit1 | RETRY | 本帧是重传 |
| bit2 | URGENT | 高优先级,可用于插队(仅急停/安全用) |
| bit3 | TS_VALID | payload 首部含有效 ts_ms |
| bit4-7 | 保留 | 必须为 0 |

### 2.5 CRC

| 参数 | 值 |
|---|---|
| 算法 | CRC-16/CCITT-FALSE |
| 多项式 | 0x1021 |
| 初值 | 0xFFFF |
| 输入反射 | 否 |
| 输出异或 | 0x0000 |
| 覆盖范围 | ver 到 payload 末尾的全部字节(不含 CRC 自身,不含 0x00 分界) |

### 2.6 长度与缓冲上限

| 参数 | 值 | 说明 |
|---|---|---|
| 最大 payload(控制链路 L1/L3) | 256 B | 超过则分片 |
| 最大 payload(流式链路 L3-L2) | 1024 B | 视频分片用 |
| 最大编码帧长 | (payload + 12) × 1.005 + 1 | 缓冲区建议静态开 1100 B |
| 接收环形缓冲 | 4 KB(STM32)/ 16 KB(P4、C5) | 覆盖突发 |

## 3. 通用交互规则

### 3.1 应答、重传与超时

| 规则 | 值 | 说明 |
|---|---|---|
| 默认超时 | 20 ms | REQ 发出后等待 RESP/ACK 的最长时间 |
| 最大重传次数 | 2(共 3 次尝试) | 仅对 `ACK_REQ` 且 type=REQ 的帧 |
| 重传标记 | flags.bit1 = 1 | 接收方据此去重(按 src+seq 判重) |
| 去重窗口 | 最近 16 个 seq | 环形记录,重传命中直接回上次结果 |
| 不可重传的消息 | 运动指令、ESTOP、心跳 | 过期指令重发有害;这些消息按"最新有效"语义处理 |

**运动指令不重传**是刻意设计:重发一条 200ms 前的速度指令比丢失它更危险。接收方只用最新一条,旧的自然过期。

### 3.2 心跳与失联判定

| 链路 | 心跳周期 | 失联阈值 | 失联动作 |
|---|---|---|---|
| L2-L1(P4 ↔ STM32) | 20 ms(双向各自发) | 200 ms 无任何帧 | STM32 进入"安全姿态",P4 记录日志 |
| L3-L1(C5 ↔ STM32) | 500 ms | 3000 ms | STM32 认为网络不可用,不影响本地运动 |
| L3-L2(P4 ↔ C5) | 100 ms | 1000 ms | P4 停止视频上行,C5 上报网络异常 |

心跳帧 `HEARTBEAT` 的 payload 携带本节点健康摘要(见第 4 节),这样心跳同时承担状态上报。

### 3.3 时间同步

```
STM32 发 TIME_SYNC_REQ(t1)                              ->  P4/C5 记 t2
STM32 收 TIME_SYNC_RESP(t1, t2, t3),本地记 t4
offset = ((t2 - t1) + (t3 - t4)) / 2
delay  = (t4 - t1) - (t3 - t2)
```

- 周期:启动后立即一次,之后每 5 s
- 结果平滑:offset 采用一阶低通(α=0.25)抑制抖动
- 若 `delay` 超过 5 ms,丢弃本次样本(链路拥塞)
- payload 用 u32 微秒计数,发送前截断为链路可承受的段

## 4. 消息目录

约定:所有多字节字段为**小端**;浮点用 IEEE754 单精度;角度单位统一为 **0.01 度**(int16)或 **度**(float,视带宽);距离单位 **毫米**(u16)或 **米**(float)。

| bit2 | NO_GAIT_CHANGE | 不允许切换步态(锁定当前步态) |

### 4.4.1 模型能力协商(2026-09-27 新增)

P4 按行为阶段切换模型(详见文档 01 §6.4)。STM32 需要的不是"模式名",而是"现在有哪些安全相关的感知在运行",所以用**能力位**而不是枚举:

| 能力位 | 名称 | 含义 | STM32 的约束动作 |
|---|---|---|---|
| bit0 | CAP_OBSTACLE | 障碍检测运行中 | 允许按正常速度上限行走 |
| bit1 | CAP_PERSON | 人员检测运行中 | 允许跟随 |
| bit2 | CAP_FACE | 人脸识别运行中 | 允许身份相关动作 |
| bit3 | CAP_GESTURE | 手势识别运行中 | 允许手势交互 |
| bit4-7 | 保留 | 必须为 0 | — |

| ID | 名称 | 方向 | 类型 | Payload |
|---|---|---|---|---|
| 0x0310 | CMD_VIS_MODE | STM32/C5 → P4 | REQ | `u8 mode; u8 required_caps; u16 max_switch_ms;` |
| 0x0311 | VIS_MODE_STATE | P4 → STM32/C5 | EVENT | `u8 active_mode; u8 caps; u16 switch_ms; u8 model_slot; u8 reserved;` |

**硬性规则(必须由 STM32 侧强制执行,不能只靠 P4 自觉)**

| 规则 | 说明 |
|---|---|
| 失能避障即限速 | 当 `caps` 的 bit0 为 0 时,STM32 必须把速度上限压到安全值(建议 ≤100mm/s)或要求静止 |
| 切换要有超时 | `CMD_VIS_MODE` 发出后若在 `max_switch_ms` 内没收到对应的 `VIS_MODE_STATE`,STM32 按"最保守能力"处理(即假设无避障) |
| 状态丢失按能力位 0 处理 | 若 `VIS_MODE_STATE` 超过 1s 未更新,`caps` 视为 0,速度上限立即收紧 |
| 能力位不是"许可",只是"事实上报" | P4 上报的是"我实际在跑什么",不是"我打算跑什么" |

## 5. 链路速率与调度预算

| 链路 | 消息 | 频率 | 单帧估算 | 带宽占用 |
|---|---|---|---|---|
| L2-L1 | CMD_VELOCITY | 20 Hz | 24 B | 0.48 KB/s |
| L2-L1 | VIS_TARGET | 10 Hz | 34 B | 0.34 KB/s |
| L2-L1 | TELEM_JOINTS(18 关节分 2 帧) | 50 帧/s | 34 B | 1.70 KB/s |
| L2-L1 | TELEM_IMU | 50 Hz | 34 B | 1.70 KB/s |
| L2-L1 | TELEM_POWER | 10 Hz | 27 B | 0.27 KB/s |
| L2-L1 | TELEM_STATUS | 10 Hz | 24 B | 0.24 KB/s |
| L2-L1 | HEARTBEAT 双向 | 50 Hz × 2 | 19 B | 1.90 KB/s |
| **L2-L1 合计** | | | | **约 6.6 KB/s(占用 3Mbps 的 1.8%)** |
| L3-L2 | 视频 H.264 720p | 按需 | 1.5-4 Mbit/s | 峰值链路压力所在 |
| L3-L2 | 遥测代理 + 音频 | 少量 | - | < 50 KB/s |
| L3-L1 | 云端遥测 | 1-5 Hz | 100-200 B | < 1 KB/s |

单帧总长 = 10(头)+ payload + 2(CRC)+ COBS 开销(每 254 字节 1 字节)+ 1(分界)。

**结论(估算)**:控制链路带宽非常宽裕(不到 2%),协议可把余量用于降低延迟(提高上报频率)而非提高速率。真正的瓶颈在 L3-L2 的视频流,需实测 SPI 吞吐。

## 6. STM32 运动仲裁状态机

略去接口定义,状态与迁移条件如下:

```
        [BOOT]
           | 自检通过 + CMD_STAND
           v
        [INIT] --自检失败------------> [FAULT]
           | 站立完成
           v
  +--> [IDLE] <---------+
  |      | CMD_VELOCITY | 速度归零且持续时间到
  |      v              |
  |   [WALK] -----------+
  |      | CMD_ACTION
  |      v
  |   [ACTION] --动作完成--> [IDLE]
  |
  |  CMD_SIT
  |      v
  |   [SIT] --CMD_STAND--> [INIT]
  |
  +--(任意状态) 急停/安全触发 --> [ESTOP] --CMD_ESTOP_CLEAR 且安全--> [INIT]
  +--(任意状态) 主链路失联 200ms --> [SAFE_HOLD] --链路恢复--> [IDLE]
```

**迁移规则**

| 规则 | 说明 |
|---|---|
| ESTOP 是唯一可从任意状态进入且必须显式清除的状态 | 清除需要 P4 发 `CMD_ESTOP_CLEAR` 且 STM32 本地安全检查通过 |
| SAFE_HOLD 不切断舵机电源 | 只停止运动并保持姿态,便于链路恢复后继续 |
| 速度指令在 ESTOP/FAULT/SAFE_HOLD 下一律回 NACK(E_LOCKED) | 防止上层误以为可以驱动 |
| 任何状态迁移都产生 TELEM_STATUS 事件 | 上层可观测,避免"黑盒" |
| ACTION 期间收到 CMD_VELOCITY | 默认忽略并回 NACK(E_BUSY);可配置为中断动作 |

## 8. 实现约束(三个节点都必须遵守)

### 8.1 对象模型与所有权

协议栈设计为**多实例对象**,每个物理链路一个实例,状态不共享:

```c
/* 概念示意,完整定义见 include/robot_link.h */
typedef struct {
    uint8_t  rx_buf[RL_RX_BUF_SIZE];   /* 调用方提供,静态分配 */
    uint16_t rx_len;
    uint8_t  tx_buf[RL_TX_BUF_SIZE];
    uint8_t  seq;
    uint8_t  last_seq[16];             /* 去重窗口 */
    rl_stats_t stats;                  /* 丢帧/CRC 错误/超长 计数 */
} rl_link_t;
```

| 所有权 | 归属 |
|---|---|
| 缓冲内存 | 调用方(whoever 定义 `rl_link_t`)静态持有,协议栈不分配 |
| 发送权 | 调用方调用 `rl_send()`,协议栈内部串行化(同一实例不可并发重入) |
| 统计计数 | 协议栈维护,调用方只读 |
| 超时与重传定时器 | 注入(port 接口),便于 PC 上打桩测试 |

**为什么不用动态分配**:三个节点都存在长时间运行的场景,堆碎片是长期稳定性风险。协议栈全部静态。

### 8.2 中断与任务规则

| 规则 | 说明 |
|---|---|
| ISR 内只做搬字节 | DMA 完成/空闲中断里把数据搬入 rx_buf 并给出信号量 |
| 解析在任务上下文 | COBS 解码、CRC、分发都在 comm_task 内 |
| 单写单读 | rx_buf 由 ISR 写、任务读,用索引分离;或双缓冲交替 |
| 发送不阻塞 | tx 由 DMA 发出;若上一帧未发完则排队,队列满则丢弃**遥测类**,保留**安全类** |
| 安全类消息插队 | URGENT 标记的帧优先发送(急停绝不能排在高频遥测后面) |

### 8.3 必须实现的失败处理

| 失败 | 检测 | 处理 |
|---|---|---|
| CRC 错误 | 校验失败 | 丢弃 + 计数 + NACK(E_CRC)(仅当能解析出头部时) |
| 超长帧 | 解码后 len > 上限 | 丢弃 + 计数,不试图截断执行 |
| 未知 msg_id | 查表失败 | 丢弃 + NACK(E_UNKNOWN_MSG),不崩溃 |
| 缓冲溢出 | rx_len 达上限仍无 0x00 | 重置接收状态机 + 计数(这是自恢复的关键) |
| 版本不符 | ver != 1 | 丢弃 + NACK(E_BADVER),速率限制(1 秒最多 1 条) |
| 重复帧 | seq 命中去重窗口 | 重发上次 RESP,不重复执行副作用 |
| 长噪声 | 连续 N 次失败 | 记录日志,链路健康度上报到 TELEM_STATUS |

### 8.4 可观测性(必须可读出)

每个链路实例至少暴露:`rx_frames`、`tx_frames`、`crc_errors`、`len_errors`、`drops`、`retries`、`last_rx_ms`。
这些计数会进入 `TELEM_STATUS` 与云端遥测,是现场排障的唯一依据。

### 8.5 测试策略

| 层级 | 内容 | 环境 |
|---|---|---|
| 单元测试 | COBS 编解码往返、CRC 已知向量、边界长度、非法输入 | PC(纯逻辑,无 HAL) |
| 协议一致性 | 用 `tools/robot_link_ref.py` 与固件互发,双向逐字段比对 | PC + 板 |
| 压力测试 | 满带宽注入、随机字节污染、截断帧、连续 0x00 | PC + 板 |
| 故障注入 | 拔线、复位对端、时钟漂移、注入 CRC 错误 | 板 |
| 长稳测试 | 72h 连续收发,观察计数是否单调累积异常 | 板 |
