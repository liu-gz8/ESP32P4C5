## 1. 显示通路打通

### 1.1 组件补丁只带了一半(差点重演两小时前的事故)

- **现象**:把适配好的 `esp_lcd_st7102` 组件复制到新工程后,检查发现补丁不完整
- **根因**:之前针对同一个问题改了**两个文件**(`.c` 和 `.h`),复制时只带了 `.c`
- **具体位置**:`include/esp_lcd_st7102.h` 里的便捷宏 `ST7102_MIPI_PANEL_BUS_DSI_2CH_CONFIG()` 仍然是旧值 `MIPI_DSI_PHY_CLK_SRC_DEFAULT`
- **后果(如果没发现)**:写 DSI 初始化时用这个宏(它本来就是干这个的),会在 `esp_lcd_new_dsi_bus` 里 `abort()`,**症状和 9-28 那次一模一样,要再花一小时**
- **发现方法**:`Compare-Object (Get-Content 本工程文件) (Get-Content 参考文件)`
- **教训**:**补丁是成组的,复制后必须逐文件对比**。"半截补丁"编译完全通过,只在运行时炸

### 1.2 帧缓冲落在哪个内存区,必须先确认

- **做法**:初始化成功后打印帧缓冲地址
- **结果**:`0x48000ac0` —— **≥ 0x48000000,即 PSRAM**
- **含义**:CPU 写的像素可能还停在 cache 里,而 DPI 硬件直接从内存读,**必须做 C2M 回写**
- **教训**:**先确认事实,再写代码**。地址落在哪个区,决定了 `disp_flush()` 是不是必须存在。如果当时图省事不打印,后面画面出现残影或撕裂,就会去怀疑 DSI 时序、怀疑面板、怀疑驱动——而真正原因是缓存没回写

**相机与显示的缓存对称关系**(值得记住):

| 场景 | 数据方向 | 需要的操作 |
|---|---|---|
| 相机 | DMA 写 → CPU 读 | `esp_cache_msync(M2C)` invalidate |
| 显示 | CPU 写 → DMA 读 | `esp_cache_msync(C2M)` writeback |

### 1.3 单缓冲直写会撕裂

- **现象**:单缓冲直写时可能出现横向错位的条纹
- **根因**:CPU 正在写帧缓冲,而 DPI 硬件同时在扫描输出同一块内存
- **处理**:调试阶段可接受;要彻底解决需双缓冲或 TE 信号同步
- **教训**:有些现象是**架构的固有属性**,不是 bug。识别出"这是设计取舍的结果",比盲目去调参数更有价值

## 3. 检测能力问题的定位与修复

### 3.1 现象

> "拿远了基本识别不出来,离近点几乎占据全屏才能识别成功"

### 3.2 三个嫌疑,先排除了一个

| 嫌疑 | 判断 | 依据 |
|---|---|---|
| 镜头畸变 | ❌ **排除** | 规格书写镜头畸变 **< 1%** |
| 软件拉伸 1.78× | ✅ 确认 | 横向缩放 480/1280=0.375,纵向 480/720=0.667 |
| 镜头失焦 | ⚠️ 高度可疑 | 规格书:**最佳拍摄距离 80cm** |

**失焦的量化估算**(f=4.2mm,N=2.0,像素 2.9µm):

```
超焦距 H = f²/(N×c) = 4.2²/(2.0×0.0029) ≈ 3.0 m
对焦 80cm 时:近端 ≈ 0.63 m,远端 ≈ 1.09 m
```

**教训**:**诊断要用排除法,而排除要靠规格书里的事实。** "镜头畸变 <1%" 这一条就把锅从镜头身上摘掉了,直接把矛头指向我们自己的软件拉伸

### 3.3 修复:换 800×800 方形模式

- **做法**:传感器模式从 1280×720 改为 **800×800**(SC2336 原生支持),显示与模型都改成等比缩放
- **结果**:**2m 处行人检出置信度 70~80%**
- **代价**:视野范围可能变窄(800×800 是裁剪还是缩放,待用屏目视确认)
- **教训**:**软件层面的一行配置,效果胜过调一堆模型参数。** 这也说明"数据对不对"永远排在"模型准不准"前面

## 4. 检测框叠加

### 4.1 坐标映射

检测框在 800×800 坐标系,帧缓冲是 480×480 → 比例 **0.6**

### 4.2 ★ 边界裁剪不能省(内存安全)

- **风险**:框可能有一部分在画面外(人站在边缘、半个人进画面)。不裁剪就直接画,**索引会越界写到帧缓冲之外**
- **后果的隐蔽性**:那块内存里可能住着**推理的输入张量**。症状不是崩溃,而是"**明明框对了,检测结果却突然变差**"——会让人去怀疑模型、怀疑量化精度,根本想不到是画框把自己写坏了
- **写法要点**:先判断"整个框是否都在画面外"(是则直接 return),**再**把越界坐标夹回边界。顺序反了的话,完全在外的框会被夹成一个点

**教训**:**绘制类代码必须有边界检查。** 这类 bug 不会崩、不会报错,只会让别处的数据悄悄变坏——属于最难查的一类

## 5. 代码仓库准备

### 5.1 ★ 安全检查:固件备份里有 WiFi 凭据

- **发现**:对 16MB 出厂固件备份做字符串扫描,搜到明文 `SSID`、`A5203`、`66668888`
- **根因**:厂商 demo 把 WiFi 凭据**硬编码在固件里**,全片备份把这段数据一起存下来了
- **风险**:推到公开仓库 = **泄露自己的 WiFi 密码**
- **处理**:`.gitignore` 排除整个 `backup/` 目录(同时解决 16MB 体积与厂商固件版权问题)
- **教训**:**发布前必须做敏感信息扫描,而且二进制文件也要扫。** 只扫源码是远远不够的——凭据、密钥、token 常常藏在固件、日志、配置转储里

### 5.2 仓库内容边界

| 内容 | 处理 | 原因 |

| 固件源码(main + components) | ✅ 提交 | 项目主体 |

| `backup/` | ❌ 排除 | **含 WiFi 凭据**、16MB、厂商固件 |

| `reference/`、`probe/` | ❌ 排除 | 厂商公开工程(有原仓库)、含构建产物 |

最终仓库约 **500 KB** —— 一个干净的、可复现的嵌入式工程该有的样子

### 5.3 `.git` 属主问题

- **现象**:`fatal: detected dubious ownership in repository` —— `.git` 属主是 `TAO\CodexSandboxOffline`,而当前用户是 `TAO\Administrator`
- **根因**:辅助工具以**另一个系统账号**的身份执行了 `git init`,创建出的 `.git` 属主不对
- **处理**:删除该 `.git` 目录、用自己的身份重新 `git init`
- **为什么不绕过**:虽然 `git config --global --add safe.directory` 能让 git 闭嘴,但属主不匹配会在后续提交、切分支、`gc` 时继续咬人,而且会污染全局配置
- **教训**:工具以不同身份操作你的仓库会留下隐患。**遇到属主问题,修根本原因(重建),而不是加例外**

### 5.4 push 被拒:远端有本地没有的提交

- **现象**:`Updates were rejected because the remote contains work that you do not have locally`
- **根因**:建 GitHub 仓库时勾选了 "Add a README file",GitHub 自动生成了一个初始提交,与本地初始提交**没有共同祖先**
- **处理(未完成)**:先 `git fetch origin` + `git show --stat origin/main` **确认远端那个提交里是什么**,再决定
  - 方案 A(推荐,不用 force):`git reset --soft origin/main` 后重新提交 —— 保留远端提交作为历史起点,线性历史,无冲突
  - 方案 B:`git push --force-with-lease`
- **教训(重要)**:
  1. **看到"远端有你没有的提交"时,先看清楚那是什么,再决定**。这次安全(只是占位 README),但在协作仓库里盲目 `--force` 会**永久丢失别人的提交**
  2. 用 `--force-with-lease` 而不是 `--force`:前者在远端被他人改过时会拒绝推送
  3. **不可逆操作前先确认目标内容**——这条和"烧写前先备份"是同一个原则

## 6. 方法论沉淀(本日新增)

1. **"能看见"是最强的调试手段。** 一个挂了两天的问题,屏亮之后三分钟就定位了。评估任何"提升可观测性"的投入时,要按它省下的猜测时间算账
2. **发布前必须扫敏感信息,二进制也要扫。** 源码干净不等于仓库干净
3. **诊断用排除法,排除靠事实。** "镜头畸变 <1%"这一条规格,直接把锅从硬件摘掉,锁定软件
4. **补丁是成组的,复制后逐文件对比。** 半截补丁能编译,只在运行时炸
5. **先确认事实再写代码。** 打印帧缓冲地址("在不在 PSRAM")决定了要不要写缓存回写
6. **不可逆操作前确认目标。** force push、覆盖远端、擦除 Flash——都是同一个原则
7. **遇到属主/权限异常,修根因,别加例外。** 例外会一直跟着你
8. **识别"设计取舍"与"bug"的区别。** 单缓冲撕裂是前者,不该当成缺陷去死磕
