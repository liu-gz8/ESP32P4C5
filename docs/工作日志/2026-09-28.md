## 1. 环境与构建(卡了最久的一类)

### 1.1 ESP-IDF 的 Python 环境是坏的

- **现象**:`idf.py` 完全无法启动,报找不到解释器
- **根因**:`C:\Espressif\tools\python\v6.1\venv` 指向 `…\Programs\Python\Python311\python.exe`,而该 Python 已从机器上卸载
- **处理**:用 PlatformIO 自带的 Python 3.11.7 新建 venv,把旧 venv 中完好的 IDF 依赖(esptool / esp-idf-monitor / kconfig / click / cryptography / pydantic 等,全是 cp311 包)整体复制进去。**全程离线,未改动机器上任何原有目录**
- **教训**:环境问题的排查顺序是"**先确认解释器/工具链能不能跑**",再怀疑代码。这类问题不解决,后面所有工作都是零

### 1.2 沙箱不把 PATH 传给 python 子进程

- **现象**:CMake 报找不到 Ninja;ccache 报 `Permission denied`
- **根因**:沙箱环境下 `python.exe` 子进程拿到的是**进程创建时**的 PATH,shell 里后加的路径不生效(而 cmd 会生效——所以只看 cmd 会误判)
- **处理**:改用 `ProcessStartInfo` **显式构造子进程环境变量**,而不是改 shell 的 PATH
- **教训**:**"在我的终端里能跑"不等于"在程序的子进程里能跑"**。判定环境问题要验证到实际执行那一层,不能停在中间层

### 1.3 其余四个环境坑(逐个击破)

| 现象 | 根因 | 处理 |
|---|---|---|
| ccache: Permission denied | 默认缓存在 `%LOCALAPPDATA%\ccache`,沙箱无写权限 | `CCACHE_DIR` 指到工作区内 |
| gen_gdbinit 报 `ESP_ROM_ELF_DIR` 未定义 | 没跑 export 脚本 | 显式设置该变量 |
| 组件管理器崩溃 `NoneType` | `ESP_IDF_VERSION` 未设置 | 显式设置 |
| git 报 `dubious ownership` | 构建用户与仓库属主不同 | 用 `GIT_CONFIG_COUNT/KEY/VALUE` 临时放行,不污染全局配置 |

**教训**:这些都是"**环境状态没有完整传递**"的同一类问题——每个工具都依赖一组隐式环境变量,少一个就报一个看似无关的错。**把环境变量集中写成一个脚本**(本项目:`tools/idf.ps1`),是唯一可持续的做法。

## 2. 硬件与串口

### 2.1 USB 串口在长时间读写中掉线

- **现象**:全片读取 16MB 时,读到约 2MB 报 `GetOverlappedResult failed (PermissionError 13)`;之后设备从系统里完全消失
- **根因**:USB 链路(线材/接口/供电)不稳定,**不是软件问题**
- **处理**:备份改成**分块 1MB + 自动重试 + 断点续跑**(`tools/backup_flash.ps1`)。实测 16 块里有 3 块需要重试才成功
- **教训**:**长耗时的硬件操作必须可续**。一次性读 16MB 失败了要从头再来;分块 + 重试把"运气"变成了"流程"

### 2.2 串口是独占资源

- **现象**:`could not open port 'COM6': PermissionError(13)`
- **根因**:自己的 `idf.py monitor` 还开着,占着串口
- **处理**:约定"我抓日志时你关 monitor,你开着时你贴日志"
- **教训**:嵌入式调试的日常。看到 `PermissionError` 在串口场景下的第一反应应该是"**谁占着它**",而不是"驱动坏了"

## 3. IDF 版本漂移与第三方代码(本阶段的重头戏)

**背景**:厂商 demo 是给 **ESP-IDF 6.0.2** 写的,我们用的是 **6.1**。以下问题全部由此产生。

### 3.1 结构性字段改名/拆分

| 位置 | 6.0 写法 | 6.1 写法 |
|---|---|---|
| ST7102 面板配置 | `panel_dev_config->color_space` | `rgb_ele_order` |
| DPI 面板配置 | `.pixel_format` | `.in_color_format` + `.out_color_format` |
| 色彩格式枚举 | `LCD_COLOR_PIXEL_FORMAT_RGB565` | `LCD_COLOR_FMT_RGB565` |
| DMA2D 开关 | `.flags.use_dma2d = true` | 删除,改为初始化后调 `esp_lcd_dpi_panel_enable_dma2d()` |

**教训**:组件升级时,**"字段被拆分/改名"比"字段被删除"更麻烦**——后者编译期就报错,前者(如 `pixel_format` → `in/out_color_format`)语义变了但不一定报错。

### 3.2 依赖声明不全

- **现象**:`esp_ipa` 报 `hal/isp_types.h: No such file or directory`
- **根因**:该组件的 `CMakeLists.txt` 没声明 `esp_hal_cam` 依赖(文件存在,只是没进 include 路径)
- **处理**:补 `REQUIRES`;**但更好的处理是升版本**(见 3.3)

### 3.3 组件版本锁死了旧 API

- **现象**:`esp_video 0.8` 用了 6.1 已删除的 `CAM_CTLR_COLOR_YUV422`
- **关键动作**:把依赖约束从厂商锁定的 `0.8.*` **放开到 `*`**,组件管理器解析到 **esp_video 2.5.0 + esp_ipa 2.4.0 + esp_cam_sensor 2.6.0**(6.1 时代版本),**源码一行没改就编译通过**
- **教训**:**"厂商锁的版本"通常只是"他们当时用的版本",不是"唯一能用的版本"。** 遇到 API 不兼容,先试升版本,再去改源码——改源码是最后手段,因为你会失去上游修复

### 3.4 ★ 最凶的一个:兼容别名导致的运行时 abort

- **现象**:板子**反复重启**(1 秒一次),每次都停在 `Initializing LCD: 480x480` 之后,打印 `abort() was called at PC 0x4007ce75`
- **定位过程**:
  1. 从日志抓两个地址:`abort() at PC` 和 `MEPC`
  2. `riscv32-esp-elf-addr2line -pfiaC` 反查 → 得到 `_mipi_dsi_ll_set_phy_pllref_clock_source`(`mipi_dsi_ll.h:238`),并且有 `(inlined by) esp_lcd_new_dsi_bus`
  3. 打开该行 → 是 `switch` 的 `default: abort();`
  4. 反推:传进来的时钟源值不在 switch 接受的五个值里
  5. 追值来源 → 厂商代码用 `MIPI_DSI_PHY_CLK_SRC_DEFAULT`
  6. 查该宏定义 → **被 IDF 重定义为 `..._DEFAULT_LEGACY`(= PLL_F20M)**,而新默认值是 XTAL
- **根因**:P4 **rev 3.0 起 DSI PHY 参考时钟方案变了**(新值 XTAL),旧值降级为 LEGACY。旧宏名仍然存在(向后兼容),**但语义变了**
- **处理**:改用 `MIPI_DSI_PHY_PLLREF_CLK_SRC_DEFAULT`
- **教训(三条)**:
  1. **`abort()` 是代码主动调用的**,说明"某个值不满足预期",**不要怀疑内存损坏**——直接把搜索范围缩到"哪个分支会主动 abort"
  2. **`_LEGACY` / `_DEPRECATED` / "for backward compatibility" 是版本陷阱高发区**:保证能编译,不保证行为
  3. **找"该用哪个常量"时,看驱动自己在什么条件下用哪个值**(`esp_lcd_mipi_dsi_bus.c` 里有 `#if HAL_CONFIG(CHIP_SUPPORT_MIN_REV) < 300` 的分支),**代码比文档更接近真相**

### 3.5 补丁要"成套"带

- **现象**:把适配好的组件复制到新工程后,bug 复现
- **根因**:上一个项目里针对同一个问题改了**两个文件**,复制时只带了其中一个(`_mipi.c` 改了,`.h` 里那个便捷宏没改)
- **处理**:用 `Compare-Object` 逐文件对比,补齐
- **教训**:**复制代码时要逐个文件对比验证,不能凭印象**。这种"半截补丁"是隐性的:编译完全通过,运行时才炸

### 3.6 第三方"便捷宏"是给特定硬件调的

- **发现**:`ST7102_MIPI_PANEL_BUS_DSI_2CH_CONFIG()` 里的 lane rate 是 `500 Mbps`(给 2.5 寸屏的),我们的屏是 900 Mbps
- **教训**:厂商的便捷宏默认绑定他们自己的板子/屏。**用之前先确认每个字段是不是你的参数**

## 4. 算法与测量(图像缩放实验)

这部分是"**测量本身出错**"的典型案例,含金量最高。

### 4.1 单位换算错了 8 倍 / 12 倍

- **现象 1**:算带宽时已经用了"每像素 2 字节",又多除了一次 8(再转一次比特→字节)
- **现象 2**:`字节 ÷ 微秒` 直接当成了 MB/s(漏了 `×10^6`)
- **教训**:**量纲要跟着算式走**,写清 `字节/帧 × 帧/秒 = 字节/秒`,让单位自己约掉。**数字与直觉差一个数量级时,先怀疑单位,而不是世界变了**

### 4.2 ★ 索引塌缩:测出来的数字完全没有意义

- **现象**:二维图像压成一维时写成 `dst[j + i]`(x + y),而不是 `dst[y * 宽 + x]`
- **后果**:
  - 102,400 个目标像素只写进了 639 个槽(**覆盖率 0.6%,数据严重丢失**)
  - 源/目标的工作集都只有几 KB,**全部落在 L1 cache 里**
  - 于是测出来的是"**在 L1 里做算术的速度**",和"处理 1.8MB 图像"毫无关系
- **纠正过程**:修正索引后,同一段逻辑的每像素成本从 **14.1 周期 → 45.6 周期**——**变慢了,但那才是真话**
- **教训(两条)**:
  1. **一维索引 = 行号 × 每行宽度 + 列号**。`x + y` 描述的是对角线,不是行主序
  2. **修好 bug 后性能数字变差,往往是好事**——说明之前测的是假的

### 4.3 先除后乘,精度被整数除法吃光

```c
size_t dx = dw / sw;      /* 320/1280 = 0  ← 归零 */
dst[dx * j ...]           /* 恒为 0 */
```
- **教训**:**整数运算里先乘后除**。先算一个小于 1 的比例系数,精度会被直接截断。**这条在定点数、PWM 占空比、坐标映射里到处都会用到**

### 4.4 缺少"测试的自检"

- **问题**:没有校验"输出是否与优化前一致",也没有检查"索引是否覆盖了整幅图"
- **补救**:引入三种自检——**哨兵图案**(源图填 `(x<<8)|y`,验证映射)、**索引范围打印**(min/max,应与理论值吻合)、**工作量核对**(迭代次数 = 输出像素数)
- **教训**:写任何基准测试前,先回答"**我怎么知道这个测试真的做了我以为它做的事**"

### 4.5 优化成果的分解(方法示范)

最终把 15 倍提速**干净地拆成两个来源**:

```
总提速 15.35× = 9.0×(工作量:少处理 9 倍像素) × 1.71×(访问宽度:16 位代替 8 位)
```

- **教训**:**性能分析的第一步不是"看缓存",而是"数清楚做了多少活"**。顺序永远是"算法级减少工作量 → 常数因子优化"
- 另一发现:**"跳跃访问"是否伤性能,取决于步长与缓存行的关系**。步长 8 字节、缓存行 64 字节时,8 次访问有 7 次命中,几乎无损

## 5. 推理集成

### 5.1 返回的"结果个数"永远是 0

- **现象**:调用方拿到 0 个目标,却照样打印结果数组
- **根因**:`*out_count` 被最后一行 `*out_count = n;`(n 从未被赋值)覆盖为 0;而调用方**没检查个数就无条件打印 `boxes[0]`**
- **后果**:**打印的是未初始化的栈内存**——日志里出现"同一个框连续 5 帧一模一样",那是栈上同一位置的残留数据
- **教训**:**"结果数组"和"有效结果个数"是一对,缺一个就是未定义行为**。打印/使用前必须先用个数判断

### 5.2 结果拷贝的循环语义错误

- **现象**:把"目标下标"和"数组槽位下标"混为一谈;`boxes->score` 实际永远是 `boxes[0]`;`if (i == det.category)` 把循环下标和类别号比较
- **教训**:**遍历结果时,n 是"第几个目标",它同时就是数组下标** —— 一一对应,不要引入第二个变量

### 5.3 像素格式选错(红蓝通道对调)

- **现象**:写成 `BGR565LE`,而相机输出是 RGB565
- **判定依据**:V4L2 的 fourcc `0x50424752` 按 `a | b<<8 | c<<16 | d<<24` 展开 = `'R','G','B','P'` → **RGB565**
- **教训**:格式类字段不要猜,**从来源(fourcc / 手册 / 驱动)反推**

### 5.4 ★ 只用日志无法判断"模型看到了什么"

- **现象**:置信度 85~95%(说明模型在工作),但框几乎覆盖整幅图
- **换算**:图像空间 `w=1188` → 模型空间 `1188 × 224/1280 ≈ 208`,即目标占输入图的 **93% × 100%**
- **结论**:坐标映射链路是对的(之前担心的"框整体偏移"可排除),但**"模型到底看到了什么"只有两种可能,日志分不出来**:
  - 场景本身太近(人真的占满画面)
  - 输入图像有问题
- **教训**:这就是文档 09 §7.4 把"**数据对不对**"列为调试第一步的原因。**在"亲眼看到数据"之前,所有关于模型的推断都是猜测**

## 6. 资源与链接

### 6.1 模型没被链接进镜像(链接器垃圾回收)

- **现象**:加了 435 KB 的模型依赖,应用镜像只涨了 **2 KB**
- **根因**:没有任何代码引用 `PedestrianDetect`,链接器的 `--gc-sections` 把"没人用的代码和数据"全丢了
- **验证**:`riscv32-elf-nm` 在 ELF 里搜不到任何 `pedestrian/espdl` 符号
- **后续**:真正写代码调用后,镜像一次从 557 KB 涨到 **3.9 MB**
- **教训**:**"加了依赖" ≠ "进了镜像"**,只有被引用的部分才会链接进来。这既是省空间的机制,也是"为什么我的代码没生效"的常见原因

### 6.2 分区不够(资源是有界的)

- **现象**:一个行人检测模型就让 4MB 应用分区用掉 **94%**,只剩 252 KB
- **处理**:重新分区(factory 4MB → 8MB,storage 12MB → 7.5MB),余量回到 53%
- **教训**:这验证了文档 09 关于"模型槽位数量受资源限制"的警告——**人脸 + 手势模型根本放不进原来的分区**。**资源约束要提前算,不能等加不进去才发现**

### 6.3 显示帧缓冲在 PSRAM,必须做缓存回写

- **实测地址**:`0x48000ac0`(≥ 0x48000000,即 PSRAM)
- **含义**:CPU 写的像素可能还停在 cache 里,而 DPI 硬件直接从内存读
- **对称关系**:

| 场景 | 数据方向 | 需要的操作 |
|---|---|---|
| 相机 | DMA 写 → CPU 读 | `esp_cache_msync(M2C)` **invalidate** |
| 显示 | CPU 写 → DMA 读 | `esp_cache_msync(C2M)` **writeback** |

## 7. 方法论沉淀(可迁移的部分)

按重要度排序:

1. **先看实际状态,不要猜。** (查文件要先 `-Force`、查进程要列出来、查端口要扫一遍)
2. **先修"仪表",再调"参数"。** 在"结果个数 / 置信度 / 索引范围 / 帧指纹"这些可观测量正确之前,任何参数调整都是赌博
3. **数据必须和产生它的代码一起审。** 拿到数字先看代码,别急着分析
4. **数字必须带单位和上下文。** `MB/s` 还是 `MiB/s`?缓冲多大?访问模式?单线程还是 DMA?——离开这些,数字没有意义
5. **编译通过 ≠ 行为正确。** 兼容别名、语义漂移、隐性依赖都属于这一类
6. **`abort()` 先找"谁主动调用它",非法访问才查内存。** 判断对类型能省大量时间
7. **复制别人的代码要逐个文件对比验证。** 补丁经常是成组的
8. **长耗时的硬件操作要可续、可重试。** 把运气变成流程
9. **把环境变量集中成一个脚本。** 隐式依赖是环境问题的总根源
10. **性能优化顺序:少做 → 做得快 → 换硬件。** 顺序反了会做大量无用功
